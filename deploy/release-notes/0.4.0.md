These notes are written for an operator who runs their own hub and whom
nobody in this project can log into (invariant 9, D161). **Nothing in
this project deploys anything.** This release makes a build available;
the operator upgrades when they choose.

## Read the records you already have

This release exists so that you can read the state root you already
have, with the records already in it, before anything about its format
moves.

Your hub keeps every job as a record on its volume: the command, the
verdict, the timings, and every output path with its size and its
sha256. Until now nothing could show you what was in there. `herd-hub
report` can, and it is in this build.

Run it inside the container that already has the volume mounted, so
nothing new is mounted and nothing is copied:

```sh
docker compose exec hub herd-hub report
```

That works without a path **if your deployment sets `HERD_STATE_DIR`**,
as the reference `deploy/docker-compose.yml` does (`/var/lib/herd`, the
path the volume is mounted on). The image bakes no such value, so if
your deployment does not set it, name the root:

```sh
herd-hub report /var/lib/herd
```

Unset and unnamed, the path falls back to the relative `herd-state`,
which is almost certainly not your root. You will not be left guessing
about that: the report prints the root it actually read on its second
line, it exits non-zero if that path is not a directory, and if the
path exists but holds no `jobs/` it says so in capitals, naming the
path, before any figure — *"THE JOBS DIRECTORY COULD NOT BE READ, so
every figure below is about no jobs at all and about nothing else"*.
Read that second line and you know which directory the numbers are
about.

What it prints, in three sections: how many records are there and how
many it could read; file-level deduplication over the bytes the records
name, against the bytes of their distinct digests; per-job output size
by decile and the maximum, never a mean; and what the records claim
against what the directories actually measure.

**What it needs from you: nothing.**

- **No new volume, and no copy.** It reads the root in place.
- **No migration.** The on-disk format is unchanged. `RECORD_VERSION`
  is **1** and the state-root layout is **1**, the same two numbers your
  current hub reads and writes.
- **No downtime.** It takes no lock of any kind — not the store's, and
  not the `flock` on `hub.lock` a serving hub holds for its whole life
  — so it runs against a hub that is up and serving. Each record is
  read whole or not at all, so no figure is torn; but the figures
  together are a point-in-time snapshot and not one instant, and the
  report says so itself at the top.
- **It writes nothing.** It opens files read-only and creates nothing.

**It reads no output byte and no log byte.** Every size and digest in
the first two sections comes out of a record; the third section's
measurements are directory lengths. So a 90 GB volume is not read
through to answer it.

### Why you can believe the paragraph above

This was tested rather than argued. A state root was created by the
**v0.3.7** binaries — a hub, a runner and four real jobs through them,
one exiting 0, one exiting 7, and one leaving three collected files —
and then **this** build's `herd-hub report` was run against that same
root, untouched. It read every record:

```
records
  job directories                    4
  records read                       4
  directories with no record yet     0
  records this build could not read  0
```

It computed real figures over records a v0.3.7 hub wrote: 3 files with a
digest, 9216 bytes named, 2 distinct sha256, 5120 distinct bytes,
`r_file` 1.80. And it reconciled them against the disk:

```
  records still claiming their bytes  1 job(s), 9216 bytes (9.00 KiB)
  every files/ directory measures     9216 bytes (9.00 KiB)
  the two agree to the byte, which is what a sound accounting looks like
```

The root was fingerprinted — every file, and the sha256 of the sorted
list of their sha256s — before and after `report` and
`retention-preview` ran. The two fingerprints are identical, so neither
command wrote a byte.

## The other thing you can run, which also removes nothing

`herd-hub retention-preview` shows what a record-retention pass *would*
remove from a root, and what it would free, per priority class. **It
removes nothing**, and that is structural: the module has no deletion
path, no `--apply`, and no flag that could later be given one.

Every span is a required argument with no default, because this build
states no retention policy of its own:

```sh
herd-hub retention-preview --merger 90d --step 14d \
  --nightly 14d --producer 14d
```

A span of `0` means that class **never expires** — not "remove it now".
The output says so in those words.

It refuses rather than guesses in the two cases where an answer would
mislead: a clock reading behind the root's own newest record, and a pass
that would leave no record behind.

## What else changed

Thirteen changes here are ones an operator or a requester can notice.
They are drawn from 334 commits and 84 merges since v0.3.7, carrying 38
recorded decisions — most of which are about how this project works and
change nothing you can observe.

**The hub**

- **`herd-hub report`**, above: a state root read without a lock.
- **`herd-hub retention-preview`**, above: what retention would take,
  taking nothing.
- **The hub says how it stops, and says how it stopped.** At startup it
  now prints its stop contract: `SIGTERM` and `SIGINT` stop it cleanly,
  it stops accepting connections and submissions, lets the dispatch
  pass in flight finish, and exits, allowing that pass at most **5 s**.
  On the way out it reports whether it made that budget. **Give the
  container at least 5 s of grace** in your own deployment. Jobs
  already running are not cancelled: they belong to their runners,
  which hold their verdicts until a hub records them.
- **Job ids are never handed out twice.** `store.json` now carries a
  high-water mark of the ids this root has minted, raised and synced
  before the directory that claims an id. Until now the next id was a
  function of what was still in `jobs/`, so a root whose directories
  went away would mint `j0000000001` again, over ids your own tracker
  and logs still name. This is the one on-disk change in this release
  and it is additive — see **Upgrading and rolling back** below.
- **Bytes that arrive again re-admit an evicted collection**, so the
  accounting of what the volume holds stops drifting after an eviction.
- **A file the hub refuses is named, never erased.** A configuration or
  capability file it will not accept is reported by path, and left
  where it is for you to look at.
- **One `fsync` fewer on the queued-wait write.** Writing why a queued
  job is waiting dropped the event `fdatasync`, about 31 % of that
  write's cost. The record itself keeps **both** its syncs, so
  `events.jsonl` can only ever fall behind `job.json` and never run
  ahead of it.

**Runners, and how the hub places work on them**

- **A runner announces how many jobs it will hold at once, and the hub
  honours it.** A hub no longer stacks more concurrent work on a
  machine than that machine says it can take.
- **A refusal at a machine's own ceiling costs the job nothing.** Being
  turned away by a full runner no longer spends one of the job's
  attempts.
- **A runner's live jobs are keyed by job *and attempt***, so a second
  attempt is never confused with the first one.
- **The watchdog measures each silence inside its own loop**, which
  stops a busy hub from reporting a healthy runner as lost.

**Requesters**

- **A verdict says which revision it really ran.** Where your own
  `fetch` hook writes the revision it reached, that revision is on the
  record and in the JSON `herdctl --verdict-to` writes.

**Getting a fix quickly**

- **A hotfix lane.** A `-dev` tag publishes a pre-release through a
  separate workflow, with a preamble on its body saying it skipped the
  merge gate and naming the branch and commit it came from. It is for
  getting a fix to you in minutes; an ordinary release is still the
  ordinary way in.

## What is **not** in this release

Read this part. Two of these are things people have expected to find.

- **There is no record-retention engine, and no disk is reclaimed by
  this upgrade.** Retention has been decided — merger records kept 90
  days, every other class 14, and active by default — but **not one
  line of the engine is written**. This build ships
  `retention-preview`, which removes nothing, and nothing else. If your
  volume is filling, this release does not empty it. Nothing in it
  starts removing records on a timer, now or after a restart.
- **Nothing in this release removes a record.** The only thing this hub
  ever removes is **output bytes**, under the output budget, and that
  is unchanged from the build you are running: both print the same
  figures at startup — 200 GB on the volume, the newest 7 days kept
  while there is anything older to remove instead. Even then the record
  survives the bytes: as the hub puts it at startup, *"A record keeps
  every path, size and digest for ever: only the bytes are ever
  removed."* A record whose bytes went is counted separately in
  `report`, under *records whose bytes were removed*.
- **The three version numbers have not moved, deliberately.**
  `PROTOCOL_VERSION` stays 2, `RECORD_VERSION` stays 1, the layout
  stays 1. All three will move before v1.0.0, and there is **no
  migration path**: a hub at a higher layout refuses to open an
  existing root, and a hub at a higher record version reads such a root
  as zero records read with every job unread, which looks like an
  answer rather than a refusal. This release is deliberately the last
  ordinary one before that line, so that you can take the reading above
  while your root is still readable.
- **"Stable" means v1.0.0**, and this is not it.
- **No second architecture.** x86_64 Linux only.
- **No change to the five declaration fields that are parsed and not
  carried.** `needs`, `leaves`, `coalesce`, `dedup_key` and `schedule`
  are still validated in `herdctl` and not acted on. If you have
  written any of them, they still do nothing.

## Upgrading and rolling back

**Your root is not converted, in either direction**, and both
directions were tested with real binaries rather than reasoned about.

Going **up**: a v0.4.0 hub opens a root a v0.3.7 hub wrote. It prints
one line saying what it did about the one field that is new —

```
herd-hub: <root>/store.json carries no high-water mark for job ids;
taking j0000000004 from the highest job directory here.
```

— and then serves. The layout number stays 1, the root's own identity
is unchanged, and every record is still there and still read.

Going **back down**: a v0.3.7 hub opens a root a v0.4.0 hub has
written. The new field is one it has no field for, so it ignores it and
reads every figure it used to read. Both were run; both served.

**Hub and runners do not have to move together.** `PROTOCOL_VERSION` is
2 on both sides, and the fields this release adds to the wire are
optional, where absent means *"it did not say"* and never a figure
guessed on the peer's behalf. A v0.3.7 runner's handshake is a
committed test fixture in this repository, asserted to decode here with
the new field read as "did not say", and the reverse direction is
asserted too. So you can upgrade the hub first, or a runner first.

There are two practical cautions. The first is the stop budget: **give
the hub container at least 5 s of grace**, or your own tooling will kill
it before it has finished the dispatch pass it is allowed to finish.

The second is an **order of operations**, and it is the reason to run
`report` first rather than last: **take the reading before you start a
v0.4.0 hub on that root.**

If a single `job.json` on the volume was left torn — a crash, a full
disk, a power cut mid-write — a hub **refuses the whole state root at
startup and exits before it binds its port**. One unreadable record
takes every healthy one with it, your container restarts straight back
into the same wall, and the records you wanted to read are behind it.
`herd-hub report` does not work that way: it **names each record it
cannot read, counts it, and goes on** to print every figure about the
rest. So the reading tells you what is damaged, where a hub start would
only deny you everything.

**This is not new in v0.4.0 and v0.4.0 does not cause it.** The same
refusal is in the build you are running today — we checked the v0.3.7
source, not just this one — and this release changes nothing on that
path. What it changes is that it asks you to open an old root on
purpose, which is the one occasion that meets it. It is a defect on our
side, we have it written down, and the fix is to set such a record aside
and keep serving rather than refuse the volume. Until that ships, the
order above is the whole of the mitigation, and it costs you one
command.
