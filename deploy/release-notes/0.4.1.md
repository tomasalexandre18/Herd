These notes are written for an operator who runs their own hub and whom
nobody in this project can log into (invariant 9, D161). **Nothing in
this project deploys anything.** This release makes a build available;
the operator upgrades when they choose.

## Upgrade your runner

This release carries one fix, and the fix is the reason to take it.

**v0.4.0, and v0.4.0 only, deletes output spools at startup.** A spool
is what a runner holds under `<data root>/outputs/` when a collection
was interrupted — the job finished, its files were being handed to the
hub, and the runner stopped before the hub acknowledged them. Those
bytes are the only copy of that job's result.

v0.4.0 shipped two halves of one startup sequence twenty-eight lines
apart. The first, the startup reaper, emptied `outputs/` on the premise
that nothing could ever ask for those bytes again. The second, the
sweep, was written in the same release to do exactly that: offer such a
spool back to the hub so an interrupted collection can finish. The
second ran over a directory the first had just cleared. So a runner
upgrading to v0.4.0 **deleted, at its first start, the spools that same
start exists to recover** — including ones the hub was still owed and
would have asked to resume.

- **v0.3.x** never had the recovery and never had the deletion. A spool
  simply stayed on disk.
- **v0.4.0** has both, in the wrong order. It deletes.
- **v0.4.1** keeps the recovery and removes the deletion. The startup
  reaper owns processes, workspaces and cgroups, and nothing else;
  `outputs/` belongs to the sweep alone.

If you are on v0.3.x and have not upgraded, go to v0.4.1 and skip
v0.4.0. If you are on v0.4.0, upgrade now: every restart of that build
is another chance to lose a result. What a v0.4.0 runner has already
deleted is gone — there is no recovering it, and that is the whole
reason this release exists.

## What a fixed runner does at its next start

It reads `<data root>/outputs/`, and for each spool it finds it **asks
the hub** rather than deciding alone:

- The hub says it is still owed those bytes → the collection **resumes**
  and completes, and the requester gets the result they were waiting
  for.
- The hub stays **silent** about it → the spool is **set aside under a
  name that says so and kept**. It is renamed to
  `<job>-<attempt>.unclaimed` under the same `outputs/` directory, or
  `.foreign-state-root` when the bytes were produced for a hub state
  that no longer exists. A spool already set aside is never picked up
  again, so the state is terminal and not a rename undone every boot.

Each start prints what it found and how large it is, and says the same
thing in words: *"no hub will ever ask for them, this runner does not
offer them, and removing them is yours to do"*. **Removing a set-aside
spool is the operator's, never ours.** Nothing in this build deletes
one, on a timer or otherwise.

Two bounds on that walk, so a start costs the same whatever a job once
wrote: the sweep stops after 50 000 directory entries and leaves
whatever it had not reached exactly as it is for the next start, and a
spool whose walk did not finish is **not** offered — a manifest missing
half its files would read as a collection the hub holds in full, which
is the one mistake here that loses bytes.

## Nothing else changed

This is a patch release and it is narrow on purpose.

- **No format change.** `RECORD_VERSION` is **1** and the state-root
  layout is **1**, the same two numbers the build you are running reads
  and writes. Nothing on disk is written differently.
- **No wire change.** `PROTOCOL_VERSION` is **2**. No frame gained or
  lost a field, so a v0.4.1 runner talks to a v0.4.0 or v0.3.x hub, and
  the other way round, exactly as before. Hub and runners do not have to
  move together, and you can upgrade a runner on its own — which is what
  we are asking for.
- **No behaviour change for a job.** The fix removes a deletion. It adds
  nothing a job can see: same confinement, same caps, same logs, same
  verdict, same output budget.
- **Everything else in v0.4.0 is unchanged and still here**, including
  `herd-hub report` and `herd-hub retention-preview`.

Rolling **back** from v0.4.1 restores the deletion, which is the defect.
There is no on-disk reason you would have to — `RECORD_VERSION` has not
moved, so an earlier image can still read the root — but there is an
operational one: do not roll back to v0.4.0 with bytes you care about
sitting in `outputs/`.

## Two standing cautions, unchanged and still owed

Neither is new in v0.4.1 and neither is caused by it. Both are on every
release body until they are fixed.

**Give the hub container at least 5 s of grace when you stop it**, or
your own tooling will kill it before it has finished the dispatch pass
it is allowed to finish.

**Take a `herd-hub report` reading before you start a hub on an old
state root.** If a single `job.json` on the volume was left torn — a
crash, a full disk, a power cut mid-write — a hub **refuses the whole
state root at startup and exits before it binds its port**. One
unreadable record takes every healthy one with it, your container
restarts straight back into the same wall, and the records you wanted
are behind it. `report` does not work that way: it **names each record
it cannot read, counts it, and goes on** to print every figure about the
rest. So the reading tells you what is damaged, where a hub start would
only deny you everything. The refusal is in the build you are running
today too; this release changes nothing on that path. It is a defect on
our side, we have it written down (ORCH-106), and the fix is to set such
a record aside and keep serving rather than refuse the volume. Until
that ships, the order above is the whole of the mitigation, and it costs
you one command.

## Where the fix is, if you want to read it

- **D211**, `docs/decisions.md` — the decision, including what it
  reverses of D180 and why both halves had a passing test while the
  feature was dead.
- `herd-runner/src/reclaim.rs` — the startup reaper. It holds **zero**
  references to `SPOOL_DIR` in this build.
- `herd-runner/src/sweep.rs` — the sweep, and
  `the_reaper_does_not_delete_a_spool_this_sweep_would_have_resumed`,
  which calls the runner's own two startup entry points
  (`Confined::prepare` at `herd-runner/src/lib.rs:2634` and
  `Session::pick_up_collections` at `:2662`) rather than standing in for
  them. Standing in for the startup path is how this shipped in the
  first place.
