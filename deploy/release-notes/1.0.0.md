These notes are written for an operator who runs their own hub and
runners and whom nobody in this project can log into (invariant 9,
D161). **Nothing in this project deploys anything.** This release makes
a build available; you upgrade when you choose, on your own machines, at
your own moment.

**v1.0.0 is the stability promise, so these notes are written to the
rule that promise lives by: every sentence below is something the code
does, measured, at a named version, on a named host.** Where a figure
was measured once, on one host, idle, or on a fixture rather than on a
fleet, it says so in the same breath as the figure. Where nothing was
measured, it says that instead of estimating. **In no direction does
Herd claim a platform, a figure or a capability it has not run.**

## Read this first: there is no migration path, in either direction

**All three of Herd's version numbers move in this release.** Every
release up to and including v0.4.1 is at protocol 2, record 1, layout 1.
v1.0.0 is at:

| Number | What it governs | v0.4.1 | v1.0.0 | Declared at |
| --- | --- | --- | --- | --- |
| `PROTOCOL_VERSION` | whether two builds can talk | 2 | **3** | `herd-proto/src/lib.rs` |
| `RECORD_VERSION` | the shape of every `job.json` in the root | 1 | **2** | `herd-hub/src/job.rs:72` |
| `LAYOUT_VERSION` | the shape of the state root itself | 1 | **2** | `herd-hub/src/store.rs:99` |

The release body above these notes prints all three on lines a script
can match. Read them off the bodies of the two releases you are moving
between, never off a page like this one.

**There is no migration path anywhere.** A hub at a higher record or
layout version does not convert an existing state root. There is no
offline migration tool, no `--migrate`, and nothing planned to add one.
**v1.0.0 assumes a reset**, and that was taken as a decision with its
price understood, not discovered afterwards.

**What actually happens is the layout refusal, and it is the stricter of
the two.** A hub reads `LAYOUT_VERSION` once, out of `store.json`,
**before it binds anything**, and does not start:

```
the state root /var/lib/herd has layout version 1, and this hub writes
version 2
```

That is the case you are in moving from v0.4.1 to v1.0.0. The hub stops
before a single record is read, so the gentler per-record behaviour this
release also ships — a record whose `RECORD_VERSION` this build does not
read is **quarantined by name and counted** rather than taken as a
reason to refuse the whole root (D218, D219) — never comes up on this
upgrade. It is there for a pair of builds that differ on the record
number alone, which no two releases do.

**And the refusal cuts both ways: it is the rollback too.** Neither the
upgrade to v1.0.0 nor a rollback from it can read a state root written
across that line. Crossing either disk number means starting on a
**fresh** root and leaving every queued job and every uncollected
verdict behind in the old one.

**Refusal by version is measured, not argued.** The record half was
proved with a control — same binary, same root: a three-record fixture
read **3 of 3** records at record version 1 and **0 of 3** at version 2,
all three named, exit 0 both times. A record this build does not read is
**refused by version, not degraded**: nothing is half-read, nothing is
guessed at and nothing is silently dropped. The layout half is stricter
still, because it refuses before anything is read at all.

### The four steps, and the first one is the only one nobody can do for you

1. **Take the reading off the old root first, with the old binary.** Run
   `herd-hub report` on it before you move anything, using the release
   whose numbers match that root. Save the output. Once you are on a
   build whose numbers differ you cannot read that root at all, and once
   the root is aside you do not get another chance. **Extract anything
   you will want later — a verdict, a log, a collected file — now,
   while the binaries that can read it are still installed.**
2. **Then move the root aside. Do not convert it and do not delete it.**
   Stop the hub, leave the old volume exactly as it is, and give the new
   hub a **new, empty** volume. Nothing is destroyed that way and the
   old root stays readable by the old binary for as long as you keep it.
3. **Expect every runner to be refused once, by name, and that is
   correct.** A fresh root mints a new state identity, so a runner
   holding a spooled verdict for the old root is holding state for a hub
   that no longer exists — the same job ids mean different jobs there.
   The runner sets such a spool aside under a `.foreign-state-root` name
   rather than deleting it, names it with its size at every start, and
   leaves the disk to you.
4. **Re-approve each runner.** The roster lives in the root, so a fresh
   root has an empty one and refuses every machine. One
   `herdctl runner approve <name>` and a new token each.

Bytes a fixed runner would never have kept are not reclaimed by any of
this either: moving the root aside is what frees them, and no migration
exists to carry them forward (D221, D242).

## What v1.0.0 does not meet, named

Five things. None of them is a surprise found at the tag; each was ruled
on, with the reason written beside it, and each is named here because a
stability promise that hides its own holes is not one.

### 1. E-49 — "a runner joins in thirty minutes" — waived, and unmeasured

**Waived by the first consumer for v1.0.0, 2026-10-30 (D248), on their
own condition that it be named here as not met.** It is named.

**The thirty minutes has never been timed on real hardware. The
measurement is zero, not large and not small.** The walk has no
automated form, so nothing in the suite stands in for it either.

**A measurement is coming and it is not this one.** They will time the
**re-enrolment of their server runner** at the v1.0.0 migration — fresh
hub, fresh runner — and send duration, steps, version numbers and the
first job's id. **Re-enrolment is not E-49's new-machine walk**, they
said so themselves, and **E-49 will not be declared met on it.** They
have been told that in writing. Whatever that report says, this row
stays unmet until somebody walks a machine that has never run Herd.

### 2. E-50 — "WSL2 a supported platform" — withdrawn, not waived

**Withdrawn by the first consumer, and the difference from a waiver is
load-bearing.** A waiver is a promise deferred; a withdrawal is a
requirement retired. Their words: *"nous n'en avons pas besoin,
l'attente a été écrite quand le parc était incertain"*.

**The reason is written here and not only the withdrawal, because
without it somebody re-adds WSL2 in six months believing they are
closing a gap.** Their fleet needs **KVM, so native Linux**: the NixOS
server with its runner in a systemd unit, and the 4060 PC whose runner
runs in a dedicated Linux boot and **not under Windows**. WSL served one
build-host experiment and **never Herd**, and that path is abandoned.

**No Herd runner has ever run on WSL2.** That is why this is retired
rather than promised: in no direction does Herd claim a platform it has
not run on.

### 3. E-14 — "warm caches ready before a job" — withdrawn, not waived

**Withdrawn by the first consumer.** Their executor already does it: a
copy-on-write mount of the nearest cache per commit, from their own `up`
step.

**Their reason, written here for the same purpose as E-50's:** *"the
requester supplies its own warm cache through its executor hook; Herd
need not know the shape of a cache."* Herd moves packs and places work;
it has no cache engine and this release adds none.

### 4. The hub's record retention — cut from v1.0.0, following in v1.1

**What ships.** Two bounds on the hub's disk, and they are real:

* **`--output-budget`** bounds the bytes a hub holds in collected
  output files, enforced when a collection arrives rather than on a
  clock.
* **`--volume-free-floor`** reads free space on the filesystem the state
  root sits on, at every trigger, and lowers the ceiling to
  `min(--output-budget, held + free − floor)`. It ships with **no
  default**: absent, not one `statvfs` is called and the budget alone
  decides, exactly as before the flag existed. A hub that cannot measure
  its volume keeps the behaviour of a hub with no floor and **says so
  once**, naming the path and the reason.
* **`herd-hub retention-preview`** answers what a retention pass *would*
  take, and what a budget *would* free, **removing nothing**. There is
  no `--apply` and no flag a later change could invert.

**What does not ship.** A time bound on a finished job's record; the
90-day merger class and the 14-day rest; the daily backstop; and a
tombstone that answers for an id that has been removed. **Nothing in
this release removes a record, on a timer or otherwise.**

**One limit stated precisely, because it is the one that surprises.**
`--volume-free-floor` *measures* the whole filesystem — it is the only
quantity in the hub that can see a record byte, a log byte and a
collected byte at once — but **the only thing a sweep can remove is
output collections.** So it detects pressure from any source, including
something that is not Herd at all, and relieves it through one lever.
If the pressure is not in the output files, the floor will say so and
will not be able to act on it.

**Why this is the right cut rather than a gap.** On the first consumer's
own root, read with `herd-hub report` on 2026-10-29: **≈ 346 MiB** of
records, logs and event files over **3 334 jobs** — about **104 KiB a
job**, **0.32 %** of the root — against **105.57 GiB** of collected
files, **99.68 %**, arriving at a derived **7.57 GiB/day**. Records are
a few gigabytes a year. Outputs are gigabytes a day. The bound that
ships is on the quantity that moves.

### 5. One known-unstable test ships, and it is named

**v1.0.0 publishes with a known-unstable test in the suite rather than
taking the fix, and this breaks one of our own release blockers.** B8
reads *"No known-unstable test ships"*. It is not met, and these notes
say so rather than wording around it.

**The test is `a_runner_killed_mid_job_gives_its_slot_back`, in
`herd-hub/tests/slots.rs`.** The question it carries is whether a runner
silent for `lost_after` keeps its link. The cause is located exactly in
the product: the hub's watchdog deletes a runner from its peers map
before asking that runner what it holds, so a runner descheduled briefly
under load is written off rather than asked (D228). The obvious reorder —
ask before dropping — was written, proved red-before and green-after on
a unit test, run against this test's own regime, and came back **5 of 5
red, unchanged**; it is withdrawn.

**The fix on the table would have cost a published promise, and that is
why it was not taken.** Giving the link its own bound of
`lost_after * 2` makes the test holdable and **doubles E-21**: a runner
nothing has been heard from for about **60 s** is lost and its jobs
attempted once more, which would have become about **two minutes** for a
machine genuinely switched off.

**The promise is unchanged.** E-21 still says about 60 s, and the
behaviour the test complains of is the product doing deliberately what
E-21 publishes. What ships is the test, named, and not a quietly widened
bound.

## What v1.0.0 is

### Invariant 2's five seconds, timed at last — and only half of it

**A runner stops cleanly in 0.212 s — idle.** Invariant 2 publishes
*"≤ 5 s when its owner asks"*, and until 2026-10-30 that bound had never
been timed against a running runner. Measured on our own queue runner,
v0.4.1, one host, one version, `kill -TERM` by PID to process exit:
**0.212 s**, a 24× margin, with the runner's own lines reading
`draining (the runner's owner asked it to stop (SIGTERM)); 0 job(s) to
end, no new job accepted` and `stopped`.

**`0 job(s) to end` is the whole scope of that measurement, and it must
be read in the same breath as the figure.** The case the bound exists
for — a runner asked to stop while a job is running, which has to end
that job, take its verdict and write it down — is **untimed**, and no
figure in this project covers it (D264). Read 0.212 s as the floor of
the stop path, not as the answer for a runner draining a three-hour
build. One host and one version is also the scope: nothing here says
what the figure is on your machines.

**Stopping the hub is bounded too and loses nothing.** It stops
accepting connections, starts no further dispatch pass, waits up to five
seconds for the pass in flight, and exits (D184). `docker compose` as we
ship it allows 20 s. **If you stop the hub with your own tooling, give
it at least five seconds of grace**, or you will kill it before it has
finished the pass it is allowed to finish.

### What a hub does when a record it cannot read is on the volume

**An unreadable record no longer takes the whole state root with it, and
this is the one behaviour change worth upgrading for on its own.** Up to
and including v0.4.1, a single `job.json` left torn — a crash, a full
disk, a power cut mid-write — made the hub **refuse the entire state
root and exit before binding its port**: one damaged record took every
healthy one with it, the container restarted straight back into the same
wall, and the records you wanted were behind it.

**In v1.0.0 such a record is quarantined**: named with its path,
counted, left untouched on disk and kept out of the queue, and the hub
comes up (D218). The same is true of a record carrying a
`RECORD_VERSION` this build does not read (D219). It was proved by
**construction** and not by sampling: all **308** on-disk states a power
cut can leave in one job directory were written byte for byte and
opened. **0** of them now make the hub refuse the root, and **176** are
quarantined.

### What else is in this release, and where to read it

The consumer-facing additions since v0.4.1, each with where its decision
is written down in `docs/decisions.md`:

* **The fleet's state is a document, not a protocol frame** — a
  `status.json` in the state root with its own `STATUS_VERSION`,
  published on change and never on a clock, and `herd-hub status` as the
  one text screen over it. Readable with no connection, no token and no
  protocol version in hand; reading it takes no lock (D215).
* **An events sink, one setting, no filter or template** — a URL or a
  command string, payload carrying its own `EVENT_FORMAT_VERSION`. It
  fires on a runner joining, a runner lost by either path, the owner's
  own switch moving, a job lost twice, and **a detached job's end when
  its submitter asked for it** — `herdctl submit --announce-end`, which
  `herdctl run` is deliberately not offered (D216, D250). Never per step
  by default: a day's count does not grow with the number of step jobs.
* **A scheduled pass is the requester's predicate, not the hub's** —
  `herdctl if-moved` submits a declared command when a named ref has
  moved since the last run it recorded, under a lock, and **refuses
  rather than guesses** when its state file is missing, unreadable or
  from another version. The timer is yours (D207, D217).
* **A dry run now answers for the dispatch too** — `herdctl would-run`
  reports the slot the job would really find, out of one real dispatch
  pass that is thrown away. Nothing is minted, nothing is written, no
  slot and no reservation is taken, verified by comparing every byte of
  the state root before and after (D261).
* **A runner binds nothing by default, and the mesh-address rule is
  enforced** — invariant 3 holds: a runner dials out for control and
  needs nothing inbound. Its content endpoint, when it exists, binds a
  private mesh interface only, never a default or public one (D222).
* **Every figure a `--help` prints is read back through its own
  constant**, so a documented default and an enforced default cannot
  drift apart (D245).
* **A refusal is measured down to one reading, or says it could not
  be** — an `EBUSY` is read rather than guessed (D259), and whether a
  job's cgroup can really carry a control is answered by a **controller
  list** and never by a file's existence (D265).
* **A measured byte figure prints as an exact count**, with a binary
  approximation beside it, and never in a unit chosen by how the number
  happens to divide (D224).
* **Pack transfer, at the edges and not through.** The protocol surface
  for packs is numbered at `PROTOCOL_VERSION` 3, the hub keys a registry
  on `(commit, key)` and publishes a manifest whole-or-absent in one
  `rename(2)`, a runner holds a content-addressed store and serves and
  fetches on the one socket invariant 3 permits, and a job is assigned
  its packs before its attempt begins (D229 to D247, D262). **No pack
  reaches a job's disk in this release**: the runner lays none out under
  `{in}` and registers none from `{out}`. The two expectations this
  would deliver are counted as partly built below, not as met.

## The scope, counted rather than asserted

The first consumer's numbered expectations hold **44** musts. Counted
against this release's tree:

| | Musts | Which |
| --- | --- | --- |
| Wholly in this release | **36** | counted row by row in `docs/coverage.md` |
| Partly built | **4** | E-12 and E-17 (packs, wired at the edges), E-16 (the hub's budget ships, per-runner budgets and keeper pinning do not), E-37 (all five of its event transitions exist in the hub; the row waits on a nightly existing before the nightly's own verdict can be shown end to end) |
| Nothing of it in this release | **1** | E-42, the push hook's producer submit |
| The consumer has released us from | **3** | E-49 waived, E-50 and E-14 withdrawn |

36 + 4 + 1 + 3 = 44. **A placed must is not a delivered one, and a
merged row is not a promise about a running system**: `docs/coverage.md`
carries the row-by-row state and `docs/status.md` the live figures.

Twelve of the musts have had an independent adversarial pass against the
real binaries. The rest are merged and tested and have not had that
pass, and that distinction is in `docs/coverage.md` rather than smoothed
over here.

**This release's own gates ran through Herd.** The four Rust gates for
its version commit — `fmt`, `build`, `clippy` and the full suite — were
submitted to our own Herd instance and each came back exit 0, with
**1 217** assertions passing, **0** failing and **12** skipped. Every
one of the twelve is a cgroup-delegation assertion this host cannot
make, and each is **printed as skipped** rather than counted as passed:
a skipped assertion is never reported as a passing one. The rule that
every build and gate goes through Herd is dated 2026-10-30, after
v0.4.1's tag, so v1.0.0 is the first release cut under it (D258).

## Three limits to know before you set a budget or write a job

Each of these is measured. The first two are open questions on our own
board; the third is a design limit with its reason written down. Each
will cost you something if you meet it without knowing it.

### A job's disk cap measures a workspace's apparent size, not bytes written

`bytes_written` on a job record, and the disk cap enforced against it,
are **the apparent size of the job's workspace**: a recursive walk of
the job directory summing file lengths, sampled every 200 ms and once
more at the end. Measured 2026-10-30 across eight probe jobs, each
differing in one path (D263):

* **A sparse file trips the cap having written nothing.**
  `truncate -s 8G` inside the workspace recorded **8 589 934 592**
  bytes against **16 384** bytes of disk actually occupied.
* **A job that leaves its workspace escapes the cap entirely.** 300 MiB
  written into the job's own working directory is counted exactly; the
  same 300 MiB written into a tree the command `cd`s to is counted as
  **zero**.
* **A capped job has no verdict and no receipt.** When the cap fires the
  job is stopped, and what it would have told you is not written down.

**So read the setting as a bound on a directory's apparent size.** If
you set a disk budget expecting it to bound I/O, it will not, and if you
set one on a job that writes sparse files it will fire on a number
nobody wrote. We have this on the board as an open question (whether the
figure should become the job's cgroup `io.stat` `wbytes`, which counts
writes wherever they land and cannot be inflated by a file that writes
nothing) and it is not decided here, because a bound that starts firing
correctly turns hosts that run jobs today into hosts that stop them.

### A requester cannot pass an environment variable to a job

**Five variables reach a job and no others: `PATH`, `LANG`, `LC_ALL`,
`TZ` and `TERM`.** There is no field on a submission for an environment
variable and no flag that adds one.

**The consequence, measured:** `CARGO_HOME` cannot be set, so a cargo
job re-downloads its registry into a throwaway `HOME` **every job**. On
the job we measured that `HOME` came to **194 282 312** bytes across
**6 491** files, of which `.cargo/registry` was **190 801 624**. The
first consumer does not pay this, because their devShell exports
`CARGO_HOME` *inside* the job, from their own executor hook. **A
requester without such a hook pays it on every job and has no way to say
otherwise.**

### Herd orders work; it bounds work only where the host lets it

A runner's memory ceiling is a real kernel ceiling **only under a
delegated cgroup v2 subtree**. Without delegation the runner falls back
to `RLIMIT_AS`, which is weaker in three named ways, and it **says so at
startup** rather than reporting a ceiling it does not have. The runner's
own startup report is the only thing that knows what your host actually
granted, and it changes when the host changes and not only when the
binary does. Read it after every restart.

The job confinement is **cooperative**: a job can write anything the
runner's user can. Full containment would need a mount namespace the
runner is deliberately not given the privilege for.
