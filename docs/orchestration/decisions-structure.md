# The decisions journal: structure, collisions, and what to do

Analysis for ORCH-003 (mandate step H5). **No migration has been done.**
Option A below is in force because it needs no change to the file; option
B waits for Alexa's word. Written 2026-10-24 against `origin/main` at
`3da48f5`.

## What the file actually is

- `docs/decisions.md`, 447 KB, 168 entries, D1 to D171. Header format:
  `## YYYY-MM-DD — D<n> <title>` (every one of the 168 matches). Entries
  are separated by `---`; the body is free prose, often with `###`
  subsections; cross-references are plain `D<n>` tokens.
- **Gaps:** D143 and D154, documented inside D145 and D162 as numbers
  three parallel branches raced for; D170, held by the open PR #67. PR
  #70 holds D172.
- **Order:** append-only, but not in number order. D148 sits after D149
  and D161 after D167, because a branch that merged late appended at the
  end with the number it had taken earlier. So the file's rule is already
  *identifier, not position* (D148, restated in D162, D165, D166), and
  strict monotonicity of the file would be a **new** rule that the
  existing file violates twice. It is therefore not enforced.
- **Numbers cited in code:** D-numbers appear in Rust comments and test
  names; renumbering an entry breaks those references silently. D145
  records having been renumbered twice.
- **The collision:** two branches in flight both read `main`'s highest
  number and both take the next one. The textual merge conflicts (both
  append at the end), and the integrator who resolves it by keeping both
  produces two entries with one number — the case the memory file of
  2026-10-23 says verification caught.

## The three options

| | A — one file, serialised writer | B — one file per decision + index | C — one file, reserved ranges |
|---|---|---|---|
| Change to history | none | the 168 entries move to `docs/decisions/` as `D001-….md` (or stay as an immutable archive) and a generated `index.md` | none |
| Who allocates | `herd-merger`, one branch at a time, at integration; branches write `D-NEXT` | same allocation problem: two branches creating `D172.md` collide as files, so an allocator is still needed | each branch gets a range from the board (e.g. D180–D184); unused numbers become permanent gaps |
| Textual conflicts | still possible at the tail, resolved by the one merger | none (different files) | still possible |
| Readers | unchanged; `grep -n '— D162 '` | one file per entry is easier to read and link; cross-references need the index | unchanged |
| Tooling | `check-docs.sh` already rejects duplicates, malformed headers and leftover `D-NEXT` | a generator for the index, a check that file name = header number, redirects for every `docs/decisions.md#…` anchor used elsewhere | the board must track ranges; check must know them |
| Reversibility | total | a migration PR of 168 files; reversible by `git revert` but every link made meanwhile points at the new layout | total |
| Cost now | zero | a day of agent work plus review of 168 moved entries | small |

## What was prototyped

`scripts/check-orchestration.sh` builds a fake corpus with D1–D3 on
`main`, two branches each appending a `D-NEXT` entry, the first allocated
to D4 at integration, the second wrongly allocated to D4 as well: the
check names the duplicate and fails; reallocating to D5 passes; the
historical gaps D143 and D154 are not flagged; the real file is never
rewritten (hash compared before and after). Run it: 57 assertions.

Option B's collision case was not prototyped as files, because the
analysis shows the allocator, not the file layout, is what prevents it;
separate files only remove the textual merge conflict.

## Recommendation (one)

**Option A now.** The project has one integrator role by design
(`herd-merger`, one branch at a time), which is exactly the serialisation
the single file needs, and the check already rejects the two failure
modes seen in history. Option B buys easier reading at the price of a
168-file migration and a redirect map for every anchor used in Rust
comments, Nix and the architecture document, for a collision it does not
by itself prevent. Revisit B when a second integrator is wanted or when
the file's size (447 KB) starts costing in context: an agent must never
read it end to end, and the brief template says so.

**If Alexa chooses B anyway:** a separate PR; the archive stays byte for
byte as `docs/decisions-archive.md`; new entries are files under
`docs/decisions/`; `index.md` is generated by a script and checked in CI;
the allocator stays `herd-merger`; a dry run on a copy must show 168
entries, 168 headers, the same dates and the same numbers before and
after; rollback is `git revert` of that one PR.

## Rules in force from this remediation

1. A branch writes a new entry headed `## <date> — D-NEXT <title>`.
2. `herd-merger` allocates the next free number above the highest on
   `origin/main` **and** on every open PR, at integration, and appends.
3. Gaps stay (D148). Nothing is ever renumbered; a wrong number gets a
   new entry that says so.
4. `check-docs.sh` fails on a duplicate, a malformed header or a leftover
   `D-NEXT`, and prints a note for every gap it does not know.

## Decision (2026-10-24, Alexa, relayed by the orchestrator)

Option A is applied now. Option B is the direction, **decided and
deferred**: A is B's prerequisite, since what makes the single file costly
is parallel writes at its tail, and separate files do not by themselves
stop two branches creating the same `D170`; the `D-NEXT` placeholder with a
single allocator does. Once the numbering is collision-free, the split is a
scripted move in a separate PR, reversible by revert, with D148
guaranteeing that a number cited in code is an identifier and needs no
rewrite. The trigger and the owner are on the board as ORCH-003. No
migration runs before Alexa's word. The analysis above is kept unchanged as
the dated comparison B will rest on.
