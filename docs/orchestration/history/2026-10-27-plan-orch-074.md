## Risks and findings

1. **My H-1 is refuted, and I reverse the recommendation it carried.**
   `11-sync-prices.md` measures one `fsync` on ext4/NVMe at **989 µs**, not the
   tens-to-low-hundreds of microseconds H-1 assumed, and the three syncs as
   **additive**: three marginals summing to 3.05 ms against a measured 3.00 ms.
   So the kept sync is not nearly free — it costs **1.03 s per pass at
   `N` = 1 000** — and the gap between M3a and the fully unsynced path is a
   factor of **21**, not the factor of 3 H-1 implied. **M3a is no longer the
   right first increment.** I recommended it on an assumption that has been
   measured away, and the amendment says so rather than defending it.
2. **But the answer is not "therefore drop all three".** `11`'s additivity
   result changes the *shape*: three independent thirds means three
   increments, and the first one should be the smallest. **Dropping the event
   `fdatasync` alone is worth ~31 % and cannot violate D103 in any
   direction** —
   the record keeps both its syncs and stays fully durable, and the event line
   can only fall *behind*, which D103 explicitly permits (*"may be one
   transition behind the record"*). It assumes nothing about the filesystem,
   keeps the integrity guarantee whole, needs no crash test of any kind, and
   needs only ORCH-052, granted. **The orchestrator's instinct about the M1
   row was right, and `11` is what makes it obvious.**
3. **A correction to `11`'s own wording, and to my brief's.** Both say M3a is
   "about a third off". `11 §8`'s own table says **64.5 % per write and 66.4 %
   per pass** — two thirds off. What is "a third" is the **kept** sync:
   1.10 ms,
   21x the 51 µs floor, 35 % of today's cost. The distinction decides whether
   M3a reads as marginal or as substantial, so it is worth getting right.
4. **`11`'s correction to `06` lands on my reasoning, and I had it wrong in the
   economics.** §0.2 dismissed the directory sync as "the 6.6 µs directory
   sync". `06` measured that with **no `rename` between the file sync and the
   directory sync**, so the directory had nothing dirty left; the real cost in
   the position `durable::write_file_with` puts it in is **991 µs on ext4,
   1.32 ms on ZFS** — about two hundred times. My safety reasoning there is
   unchanged (losing a rename yields the whole old record); the arithmetic is
   corrected in the amendment.
5. **And that correction exposes a hazard I had under-rated, which strengthens
   one of my tasks.** For a **decisive** write the directory sync is
   load-bearing for D103: `sync_all` makes the record's bytes durable but only
   `sync_dir` makes its *rename* durable, so a transition written without it
   could be lost while its `events.jsonl` line, still carrying `sync_data`,
   survives — `events.jsonl` genuinely **ahead** of `job.json`.
   `durable.rs`'s own comment says it: *"The name, too, has to survive: without
   this the rename itself can be lost while the file's contents are safe."*
   **So the directory sync stays unconditionally on every decisive write**, and
   the ordering oracle (ORCH-079) is the task that catches anyone dropping it.
   It is worth more than when I proposed it, not less.
6. **What survives `11` untouched.** §1's five facts and §2's hazard are
   readings of the code, not figures. §3's documentation finding is a reading
   of a man page and a `/proc` file. **`07`'s shape survives**: `11 §8` says
   three seconds of durable writing in one pass is still the dominant cost of
   that pass, so the keeper's argument holds with a 3x smaller baseline.
7. **§8 item 5 was right in direction, wrong in size.** I said stop quoting
   9.97 s for the deployment. The correction is **3.2x, to 3.128 s**, not the
   order of magnitude I suspected — **and the problem does not go away.**
8. **The larger hazard I found stands, and no figure touches it.** A `job.json`
   that comes back empty or torn makes the hub **refuse to start on the whole
   state root**: `read_stored` parses the version probe with `?`
   (`store.rs:1141-1142`) → `recover` (`:899`) → `open` (`:436`), stated at
   `job.rs:27-32`; D52's quarantine covers **labels only**
   (`store.rs:1150-1157`).
   It lands on exactly the jobs at risk (`store.rs:883-899`, `:2024`). So
   `07 §3 C`'s *"what is given up is only survival of a power cut"* is false as
   written — true of a lost field, not of a lost file. **This is why step C is
   a separate decision and may never be taken.**
9. **`09` and `11` are both taken; this piece is `10`.**
   `09-runner-self-limits.md` is on `origin/c5-announced-job-ceiling`;
   `11-sync-prices.md` is PR #90. **`README.md`'s index table has no row for
   `10` or `11`** — a `herd-step`'s or the integrator's write, not mine.
