### And the link drop is not earning its place

The proactive drop's stated purpose is in its own comment —
"dropped, so that the name is free for the runner that is dialling" — but
**the name is already freed on demand, elsewhere, by a better instrument.**
`register_runner` (`server.rs:1750`) displaces a quiet incumbent when the
replacement actually dials, at **half** the threshold:

```rust
                let quiet_for = incumbent.last_health.elapsed();
                let gone_quiet =
                    incumbent.reports_seen > 0 && quiet_for > self.policy.health_is_stale_after();
```

with `health_is_stale_after() == lost_after / 2` (`server.rs:548`). So a
runner that is genuinely gone has its name taken by its replacement's own
dial, on evidence that a live process is asking for it — which is a party's
word, not a clock. The watchdog's drop adds nothing to that case and is the
only thing that harms the late-but-alive case.

**Why this is a product defect and not a test problem.** A runner descheduled
past `lost_after` — a two-core CI box, a host under memory pressure, a runner
at a low CPU weight — loses **every attempt it holds** and has its connection
kicked, with its last go spent, although it is alive and answering a moment
later. The test is where we happen to see it; the consumer would meet it as
jobs failing on a machine that was busy.

## Risks and findings

1. **The defect is wider than the test.** It is not "V3 is fragile": it is
   that a healthy runner descheduled past `lost_after` loses its attempts.
   The shipped consequence is a job failed on a machine that did nothing
   wrong, and the hub's log says `dropping the connection to runner <name>:
   nothing has come back on it for ~2s`. That sentence in the field is this
   defect, not a flake.
2. **Two source comments will be wrong the moment the pass is reordered.**
   `WhatTheRunnerSays::NotYetSaying`'s doc and `what_the_runner_says`'s doc
   both assert that the link check runs first and that reports older than the
   threshold "cannot arise here". Whoever fixes this must rewrite both, or
   leave a comment that lies about the order.
3. **`health_is_stale_after()` is `lost_after / 2`, and it is the one place
   the hub already prefers a party's word.** If a separate link threshold is
   added, these two figures want reading together; a link threshold below
   `lost_after / 2` would make the watchdog drop a runner before its
   replacement could displace it, which is today's behaviour by another name.
4. **V3 will stay red on CI until the product changes**, and a reader who
   meets it should look for `no runner is connected to this hub` in a
   `waiting_for`. The register says so already; nothing on this branch
   changes it.
5. **I did not re-measure, so I cannot refute the 0/40.** I checked what it
   is about and what it is attached to; I did not re-run it. If the
   orchestrator wants the figure re-taken on `1a8c1ae` rather than `5d422bf`,
   that is a separate heavy task and it needs the host.

## Decisions needed

**One, and it is the product's — the same question `v3v4-rates` raised, now
located one level deeper.** Not "should `--lost-after` do two jobs" but:
**should the watchdog delete a runner's word before asking it?**

- **Recommendation: ask first.** In `one_watchdog_pass`, run the attempt loop
  over the peers as they are, then drop the silent links — or gather each
  silent runner's word before removing it and pass that word into
  `what_a_runner_says`. This is the smallest change, it needs no new flag, it
  restores D169 in the one case D169 was written for, and it makes the test's
  premise hold without touching a threshold. A runner that is truly gone
  still loses its attempts: its word then says `NotAnyMore`, or there is no
  word at all.
- **Fallback:** a second threshold for the link alone, defaulting to a
  multiple of `lost_after`. Cheaper to reason about, but it leaves a healthy
  runner's attempts decided by a clock and only moves the clock.
- **Either way it is a `herd-hub/src/server.rs` change**, so it is whoever
  holds that file, serialised behind them — not this branch.
