Filled by `herd-release` on 2026-10-29, on branch `cut-v0.4.0`. Every
figure below was measured on this branch, by the command named beside
it. `herd-release` prepares and never publishes: no tag was created, no
release was published, nothing was deployed, and no pull request was
opened.

on 2026-10-15 and have never recreated, before the three version
numbers move and that root stops being readable.

## 2. The three numbers, read from the source as `release.yml` reads them

**None of the three moves in this release**, which is not a preference
but a written constraint: **D199** and board row **ORCH-156** both say
in so many words that *the ordinary release before v1.0.0 ships at
layout 1 and record 1*.

| Constant | File:line | At `v0.3.7` | On this branch |
|---|---|---|---|
| `PROTOCOL_VERSION` | `herd-proto/src/lib.rs:114` | 2 | **2** |
| `RECORD_VERSION` | `herd-hub/src/job.rs:52` | 1 | **1** |
| `LAYOUT_VERSION` | `herd-hub/src/store.rs:59` | 1 | **1** |

The first two were re-read with `release.yml`'s own `sed` expressions,
run verbatim against this tree, including its single-declaration guard:

```
PASS: PROTOCOL_VERSION = 2 (single declaration, out of herd-proto/src/lib.rs)
PASS: RECORD_VERSION = 1 (single declaration, out of herd-hub/src/job.rs)
the source says PROTOCOL_VERSION 2, RECORD_VERSION 1
```

Why this matters, from D199, both halves measured there and neither
invented here: a **layout-2** hub refuses to open an existing root, so
there would be nothing for `report` to read; and a **record-2** build on
a version-1 root exits **cleanly** with `read = 0` and every job
`unread`, which looks like an answer rather than a refusal.

## 4. What `main` carries since `v0.3.7`

Measured with `git rev-list --count v0.3.7..origin/main` and
`--count --merges`:

- **334 commits**, of which **84 merge commits**.
- **38 decisions**, D172 to D209 contiguously.
- **13 changes an operator or a requester can notice.** This count is
  mine, built by classifying all 38 decisions against whether code
  landed for them. A figure of **"fourteen unreleased changes"** has
  circulated in this project; it is unverified and was not adopted. The
  classification itself is a judgement, which is why the 13 are listed
  one by one in the release body rather than only counted. One candidate
  was dropped on inspection: **D183** reads as a shipped change but is
  mostly a *direction* for the unstarted keeper architecture — only its
  step A (the event `fdatasync` drop) shipped, and that is what is
  announced. **D202** was dropped entirely: the hub still prints the
  output-floor promise (`herd-hub/src/main.rs:427`), and board row
  **ORCH-101** says that line may not change before the retention engine
  lands.

## 5. Open work this release leaves out

**No pull request is open.** The project stopped using them on
2026-10-28 (*One landing per batch*, D189); `main` moves by one
`--no-ff` merge per batch. So there is no open-PR list to report, and
the question "what is left out" is answered by the board instead.

Left out, and named in the release body under *What is not in this
release*:

- **The retention engine (ORCH-098, D201).** Decided — merger 90 days,
  every other class 14, active by default — and **unstarted**. Its four
  dependent rows (ORCH-099, ORCH-100, ORCH-101, ORCH-102) are all
  `owed`. This is the one most likely to be assumed present, so the body
  says plainly that no disk is reclaimed.
- **The version triple (D199, ORCH-156)** — deliberately after this
  release.
- **Five declaration fields parsed and not carried (ORCH-148)** —
  consumer-visible, and unchanged here.
- **A torn `job.json` still refuses the whole state root (ORCH-106).**
  Not a regression and not new, but it is the sharpest thing an operator
  could hit while reading an old root, so it is in the handoff's
  findings.

## 6. Proof that this release cannot destroy their records

Their root is the only copy of their evidence and is kept until v1.0.0.
Read rather than recalled:

- **`herd-hub/src/retention.rs` contains no write of any kind.** A grep
  for `remove_`, `unlink`, `truncate`, `set_len`, `OpenOptions`,
  `File::create` and `fs::write` over that file returns **0**.
- **No retention engine exists.** The only match in `herd-hub/src` for
  an engine, a pass, a daily clock or an `--apply` is the doc comment
  saying there is none.
- **v0.4.0's hub ships exactly two subcommands**, `report` and
  `retention-preview`, and both are read-only.
- **The one removal path that does ship is output-byte eviction** under
  the 200 GB output budget. It is **not new**: `evict`, `held_more` and
  `remove_tree` are all present at `v0.3.7`, and both builds print the
  same budget and floor figures at startup, so this upgrade does not
  change when or what it removes. It removes bytes and never the record
  — it renames to `files.gone/`, writes `outputs.removed` with the time,
  the reason and the byte count, and appends an `outputs_removed` event.
  The hub states this itself at startup: *"A record keeps every path,
  size and digest for ever: only the bytes are ever removed."*
- **Measured, not asserted:** the whole v0.3.7-written root was
  fingerprinted before and after this build's `report` and
  `retention-preview` ran. Identical, 23 files both times:
  `a5b45fc172d7385da7d8f556a8c47d2680eeda2408f60623616307a0df6d23fc`.
