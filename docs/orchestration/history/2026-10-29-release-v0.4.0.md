**Both directions of the upgrade were run.** A v0.4.0 hub opened the
v0.3.7 root on a copy, printed one line — *"store.json carries no
high-water mark for job ids; taking j0000000004 from the highest job
directory here"* — kept `layout_version` 1 and the root's identity, and
still read all four records; `store.json` gained `"ids_minted":4`. Then
a **v0.3.7** hub opened that same v0.4.0-written root and served: its
`StoreFile` has no `deny_unknown_fields`, so it ignores the new field.
Forward and backward both work, and `ids_minted.max(highest_on_disk)`
(`store.rs:1048`) means a rollback that mints further ids cannot cause a
reuse on the way back up.

**v0.3.7 cannot do any of this**, which is why the release exists:
v0.3.7's `herd-hub --help` prints `Usage: herd-hub [OPTIONS]` with **no
`[COMMAND]`** and no subcommands at all.

**No deletion path ships, with one precise exception, read rather than
recalled.** `herd-hub/src/retention.rs` contains **zero** matches for
`remove_`, `unlink`, `truncate`, `set_len`, `OpenOptions`,
`File::create` or `fs::write`. No retention engine exists anywhere in
`herd-hub/src`. v0.4.0's hub ships exactly two subcommands, `report` and
`retention-preview`, both read-only. The exception is **output-byte
eviction** under the 200 GB budget (`evict`, `held_more`, `remove_tree`
in `store.rs`) — which is **not new**: all three are present at
`v0.3.7`, and the two builds print identical budget and floor figures at
startup, so this upgrade changes neither when nor what it removes. It
removes bytes and never a record. Measured proof that the read commands
are read-only: the whole root fingerprinted before and after `report`
and `retention-preview`, identical at
`a5b45fc172d7385da7d8f556a8c47d2680eeda2408f60623616307a0df6d23fc`, 23
files both times.

## Risks and findings

1. **`main` was red for its three previous landings** — ci.yml runs
   40857453150 (batch 2), 40762764493 (the gate batch) and 40720983497
   (#106) all failed. `6036d24` is green. A red `main` blocks a release
   (workflow.md), so this release is possible because of a verdict that
   is hours old; if `main` moves before the tag, the green must be
   re-checked against whatever it moves to.
2. **A torn `job.json` still refuses the whole state root** (ORCH-106,
   `store.rs:1141-1142` → `:899` → `:436` → `main.rs:224`). Not new and
   not a regression, but it is the sharpest thing an operator can hit
   while opening an old root, and this release is the one asking them to
   open one. `report` is not affected the same way — it counts what it
   cannot read instead of refusing — which is a reason to prefer
   `report` over starting a hub as the first thing they do.
3. **D202 is in this release's decisions and not in its behaviour.** The
   hub still prints the output-floor promise
   (`herd-hub/src/main.rs:427`), and ORCH-101 says that line may not
   change before the retention engine lands. It is therefore absent from
   the release body, deliberately. Anyone reading D172-D209 as a change
   list will over-count.
4. **The "fourteen unreleased changes" figure was not adopted.** My
   count is **13**, built by classifying all 38 decisions against
   whether code landed. D183 was nearly over-counted (it is mostly a
   direction for the unstarted keeper work; only its step A shipped) and
   D202 was dropped for finding 3. The classification is a judgement,
   so the 13 are listed individually in the body rather than only
   counted.
5. **`report` with no state root named is safe, and was tested both
   ways** because the release body tells an operator to run it. With
   `HERD_STATE_DIR` unset it falls back to the relative `herd-state`:
   if that is not a directory it **exits 1** naming the path, and if it
   exists but holds no `jobs/` it prints *"THE JOBS DIRECTORY COULD NOT
   BE READ, so every figure below is about no jobs at all and about
   nothing else"* in capitals, with the path and the errno, before any
   figure. So the zero-record case cannot read as an answer. Worth
   recording because the image bakes no `HERD_STATE_DIR` — only
   `deploy/docker-compose.yml` sets it — and the body now says to name
   the root if the deployment does not.
6. **`deploy/`'s `0.3.3` examples were left on purpose**, on the stated
   reason in `env.example` and `deploy/README.md` that they are not
   re-dated every release. If Alexa would rather they tracked the
   workspace, that is a one-line change and a reversal of a standing
   choice, not an oversight here.
