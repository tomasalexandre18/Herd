## Risks and findings

1. **This body will not reach the published page by itself, and no
   agent can put it there.** `release.yml` builds the body from
   `body-dev.md` + `body-head.md` + `body-image.md` + `body-tail.md`,
   all of which it generates or `cat`s from `deploy/release-notice.md`,
   and it **reads no prepared file**. That is how v0.4.0 published at
   13:50:10Z missing both operator cautions. **D210** makes completing
   a published release's notes **Alexa's own act**: the auto-mode
   classifier refused `herd-step` the one `gh release edit --notes-file`
   and `orchestrator-guard.sh` refused the orchestrator the same
   command, both correctly, and D210 says neither wall is to be
   weakened. So the release order is land, tag, **paste**, in that order,
   so the page is never public and incomplete in between. ORCH-162
   retires this; its drafted shape is a per-release
   `deploy/release-notes/<version>.md` that the workflow `cat`s as a
   fourth piece, and **nothing here was designed around the gap** so as
   not to collide with it.

2. **Two RED gate runs preceded the green one, both host state, and the
   second nearly produced a wrong conclusion.** Run 1 (load1 7.00 →
   10.51): 38 failures, 34 at `herd-hub/tests/real_herd/mod.rs:805` and
   `:957` — ORCH-107's two `PATIENCE` wait sites, whose line numbers
   have drifted from the `:649`/`:789` the row names — with the tests
   printing their own diagnosis, `host load average 29.35 / 19.96 /
   11.22 over 12 cores`. Run 2 (load1 2.27 → 3.77, at-rest skips, both
   flood benches ran): 13 failures, so **not** contention on the face of
   it. `slots`' single failure is
   `real_herd::a_lend_this_host_can_really_make` **asserting rather than
   skipping** — ORCH-069's deliberate design — because `chatons.slice`'s
   `memory.high` of 18 GiB already held **16.7 GiB**, leaving 1.2 GiB
   where the fixture needs 2 GiB. **A control run of the full gate on
   the unmodified base `cd0f1b7` came back GREEN**, which made "the
   branch is red and the base is green" the obvious reading — and it is
   wrong. A third run of the branch's own gate, same sha, came back
   **GREEN** (load1 3.85 → 2.08). So the red runs were samples of a
   loaded host and the base's green was a luckier moment, not a
   difference between the trees. A nine-line version-string change has
   no path to either failure mode. **The lesson is the method's, not
   this release's: one red run plus one green control is not a
   comparison.** ORCH-107 and ORCH-069 both remain open and both remain
   able to redden a landing's gate on this host whenever the siblings
   or the consumer's production are loading the slice.

3. **The gate's own preflight ceiling is not enough headroom for the
   suite.** `scripts/bench-preflight.sh` passed at load1 8.33 and the
   run that followed went to 29.35 and red. It passed again at 2.27 and
   that run was also red. Only a run started at genuinely low load, with
   the slice's memory free, was green. `bench-preflight.sh` guards the
   *start*; nothing guards the middle. Worth a row if a landing's gate
   keeps costing a re-run.

4. **Nothing here proves the artefacts.** The static-linking
   assertions, the `archlinux` and `alpine` distribution smokes,
   `nix build .#hub-image` and `image-smoke.sh` need `release.yml`'s
   runner, and nothing local reproduces them (D162, D168). They were
   green on `40885270441` and this branch changes none of their inputs
   beyond the version string.
