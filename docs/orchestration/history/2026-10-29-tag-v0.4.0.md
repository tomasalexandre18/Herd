## Risks and findings

### The published body is missing the v0.4.0-specific half

`release.yml` assembles the body from three pieces it generates itself —
a dev preamble (empty on this lane), the install/version head, and
`deploy/release-notice.md` quoted in whole (D132). It never reads
`docs/orchestration/history/2026-10-29-release-v0.4.0-body.md`:

```
$ grep -rn 'release-v0.4.0-body' .github/ scripts/
(no match)
```

And `deploy/release-notice.md` is the standing install notice, not this
release's notes: its headings run *What you downloaded* → *The files* →
… → *Taking the machine back*, with no v0.4.0 section among them.

`herd-release`'s own handoff says so plainly, at
`docs/orchestration/history/2026-10-29-release-v0.4.0.md` line 33:

> `docs/orchestration/history/2026-10-29-release-v0.4.0-body.md` — the
> human half of the release body, **for whoever publishes to paste
> above** the half `release.yml` generates.

The body file repeats it in its own second paragraph. So the paste is a
manual step. **The orchestrator has stated that this gap is its own**:
`herd-release`'s handoff said the paste was needed and the brief for
this task did not carry it. Nothing about the artefacts is affected.

Measured against the published body (523 lines, pulled with
`gh release view v0.4.0 --json body`), every marker of the human half is
absent:

| looked for | in the published body |
| --- | --- |
| `Upgrading and rolling back` | ABSENT |
| `Read the records you already have` | ABSENT |
| `What is not in this release` | ABSENT |
| `herd-hub report` | ABSENT |
| `retention-preview` | ABSENT |
| `5 s of grace` | ABSENT |
| `take the reading before you start` | ABSENT |
| `high-water` | ABSENT |

**What that costs the operator**, concretely — these are the two
cautions the brief asked to be checked for, and neither is on the page:

1. **The 5 s stop budget.** The hub allows its in-flight dispatch pass
   at most 5 s and reports whether it made it; a deployment that gives
   the container less grace kills it mid-pass. Nothing in the published
   body says to raise the grace period.
2. **The order of operations.** `report` is meant to be run *before* a
   v0.4.0 hub is started on an old root, because one torn `job.json`
   makes a hub refuse the whole state root at startup and exit before
   binding, while `report` names the bad record and prints every figure
   about the rest. This is not new in v0.4.0 and v0.4.0 does not cause
   it, but v0.4.0 is the one release that asks an operator to open an
   old root on purpose, which is the occasion that meets it. The
   published body does not carry the order, so the mitigation is not in
   front of the person who needs it.

Also absent, and material to a reader deciding what this upgrade does:
the statement that **no record-retention engine ships and no disk is
reclaimed** (*What is not in this release*), and that the three version
numbers deliberately have not moved.

### 2. Board row: the per-release notes file should be a gate, not a memory

Drafted here at the orchestrator's request, for a planner to pick up.
Whether it becomes a decision is Alexa's, and the implementation is a
later landing's.

> **A release's own notes are a file the gate checks for.** `v0.4.0`
> published with its generated half and the standing notice, and
> without the half written for it, because `release.yml` has no input
> for a release's own notes and the step that supplies them is a human
> remembering to paste. That human was briefed for the tag and not for
> the paste, and the page went out missing both operator cautions —
> the 5 s stop grace and the order of operations that protects an old
> root from the torn-`job.json` startup refusal.
>
> The shape that turns it into a gate: a per-release
> `deploy/release-notes/<version>.md`, `cat`ed by `release.yml`
> between its generated head and the standing notice — the one place
> the body is already assembled from three pieces, so this is a fourth
> and not a new mechanism. `check-docs.sh` asserts that a file exists
> for the workspace version, so a version bump that forgets its notes
> goes red **before** a tag is pushed rather than after a release is
> public. Absent-means-no-half can stay the rule for the `-dev` lane,
> which has a preamble of its own.
>
> Why it is worth a row: the failure is silent, it is only visible on a
> public page, and the remedy after the fact is an edit to something
> people may already have read. It also moves the release's notes into
> the tree the gate runs on, where a reviewer sees them in the diff
> instead of in a handoff.
