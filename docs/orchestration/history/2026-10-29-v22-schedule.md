## Done

`herdctl if-moved` submits a declared command **if a named ref has moved
since the last run it recorded**, and says so when it has not. E-41's
predicate, on the requester's side only: **no hub file and no runner file
is touched** (D106, D207).

- **`herdctl/src/moved.rs`** (new, 888 lines with its tests): the
  predicate, the state file and the lock.
  - the state file is small JSON carrying its own
    `state_format_version`, the ref and the command it answers for, the
    commit, the time and the job id;
  - **the ref is read once**, and that one sha is three things: what the
    predicate compared, what the job builds, and what the file records;
  - **every way the file can be wrong is a refusal naming it** —
    missing, unreadable, another format version, another ref, another
    command, a commit that is not forty hex. None of them is read as "the
    ref moved";
  - **one run at a time, enforced**: `decide` takes an exclusive
    `flock`-shaped lock on `<state>.lock` and hands it back inside
    `Decision::Moved`, so the compiler keeps it alive across the
    submission and the record. A second run gets `Decision::AnotherRun`,
    submits nothing and says so. The kernel drops the lock when the
    process ends, however it ends, so nothing goes stale;
  - `--init` (`begin`) starts a file at the ref's tip and submits
    nothing; a file that exists refuses rather than being replaced;
  - the write is `write` + `sync_all` + `rename`, so a reader never sees
    half a file.
- **`herdctl/src/checkout.rs`**: `Checkout::tip_of_ref` (+
  `full_name_of_ref`), 71 lines added at the end of `impl Checkout`. It
  insists on a **ref**: a hash is refused for what it is (a hash can
  never move) and a ref that does not exist is refused by name (a ref
  that is not there has not moved). It says nothing about the tree or any
  remote — E-08's two refusals still happen once, on the way out,
  through the existing `Checkout::resolve`.
- **`herdctl/src/declaration.rs`**: `Commands::schedule_of`, 19 lines
  after `Commands::resolve`. Reads a command's declared schedule without
  a commit, because the predicate must know **which ref** before there is
  a commit to resolve. An unknown command refuses with `no_such_command`,
  the same sentence as everywhere else. This is the first consumer of
  `schedule`, one of ORCH-148's five parsed-and-discarded fields: its
  `if_moved` is now read, as the default for `--ref`.
- **`herdctl/src/main.rs`**: `Action::IfMoved` (the variant with its long
  help) and its dispatch arm, plus `watching_for`. The submission goes
  through the **existing** `submitting()` with the predicate's sha as
  `Declaring::commit`, so the declared line, labels, figures, level,
  deadline, dirty-tree and unpushed refusals are all the ones that were
  already tested. Three documented stderr prefixes (`herdctl: moved:`,
  `not-moved:`, `another-run:`), all exiting 0.
- **`herdctl/src/lib.rs`**: `pub mod moved;` — one line.
- **`herdctl/tests/if_moved.rs`** (new, 515 lines): the acceptance,
  through the real binary. **`herdctl/tests/fixture/mod.rs` is not
  touched** — the tests pass `--ref` explicitly and the fixture's own

- **`docs/scheduling.md`** (new, 200 lines): the user-facing

## The one honest deviation

**E-41 asks for the 05:00 skip to be reported as an event, and a skip that
submitted nothing cannot be one.** The hub emits events about jobs it
knows; a run that submits nothing leaves it with nothing to emit, because
it never heard of the job. So that skip is `herdctl: not-moved:` on the
timer's own stderr and nothing else. **No hub work closes this**, and the
sibling task building the event sink must not be expected to carry it.

The skip that **is** an event is the other one E-41 wants, and it needs
nothing new: a pass submitted with `--deadline 05:00+02:00` that no
machine started by then ends `cancelled (deadline)`, exit 125, with the
reason naming what it was waiting for (E-09, D40) — a real job, a real
record, a real event. Both halves are written down in
`docs/scheduling.md` ("The one thing E-41 asks for that this cannot
give", with a two-row table), in the `herdctl if-moved --help` long text,
and in the E-41 note of `docs/coverage.md`.

## Risks and findings

- **A `flock` is lent to a `fork` until the child `exec`s, and it cost a
  flaky test before it was found.** Measured on this host, with
  `/proc/self/fd` read at the moment of the refusal: `try_lock` returned
  `WouldBlock` while **no descriptor in the process held the lock file** —
  1 run in 10 of `cargo test -p herdctl --lib moved::`, where ten tests
  fork `git` continuously. The mechanism is the standard one: a `flock`
  belongs to the open file description, a `fork` duplicates it, and the
  copy goes only at the child's `exec`; this module and the submission
  after it both run `git` under the lock. So one reading of
  `EWOULDBLOCK` is not evidence of another run.
  **What was done:** `hold()` asks ten times over half a second before it
  believes it (`HOLD_ATTEMPTS`, `HOLD_PAUSE`), which is written out in the
  constant's own comment with the measurement. **It weakens nothing** — a
  real holder holds across its whole decide-submit-record, orders of
  magnitude longer — and **it was not the test being wrong**: a product
  that printed "another run holds this pass" off a microsecond-wide window
  would be printing a falsehood. Re-measured after the change: **0
  failures in 30 runs**, against 1 in 10 and 2 in 10 before it.
  *What this is not:* it is not a hole in the guarantee. The only process
  that can lend this lock out is the one holding it, and the only other
  party asking is a genuine second run, which must be turned away in any
  case. The retry removes a false "held", never a true one.
- **The tests found three defects that review had not**, and they are
  worth naming because each was a wrong answer and not a wrong test:
  1. **`--symbolic-full-name` echoes `--end-of-options`.** In that mode
     `git rev-parse` prints back every argument it has no ref for, the
     marker included, so the output for a perfectly good ref is two lines
     with `--end-of-options` first (git 2.54.0). Reading the trimmed whole
     output refused **every** ref there is. Now the **last** non-empty
     line is read, with the marker kept, because without it a ref whose
     name begins with a dash would be read as an option.
  2. **The ref was resolved after the state file.** A hash handed to
     `--ref` was then refused for disagreeing with the file rather than
     for being a hash, and a mistyped ref in a tree with a stale file
     reported the file. The order is now lock, **ref**, state — which is
     the order `Checkout::resolve` already uses for a name against a
     tree, and for the same reason.
  3. **A refusal said nothing about whether a job existed.** The
     `learn(Nothing)` was inside the submitting branch, so a timer told
     "your state file is missing" got no `herdctl: no-job:` line — the
     one documented sentence that says running again is safe. It is now
     at the top of the command, `--init` excepted.

- **A dirty checkout refuses the submission, and nothing records it.**
  `if-moved` submits through the same door as `herdctl submit --command`,
  and that door refuses a tree with tracked changes in no commit (E-08,
  no flag past it), even though the commit being submitted is a ref's tip
  and not the working tree. Nothing is recorded when it refuses, so the
  next run retries — but a pass whose checkout is left dirty will not run
  at all. **Deliberate**: reusing the tested door was worth more than a
  second resolution path, and E-08 says plainly that nothing gets past
  that refusal. Written down in `docs/scheduling.md`, "Two sharp edges".
- **One residual window: a job submitted whose record could not be
  written.** The order is submit, print the id, then record, with the lock
  still held. If the write fails, the job exists and the file does not say
  so, so the next run submits the same commit again. The sentence is loud
  and names the job and the file, and the id is already on stdout. It is
  this way round on purpose: recording first would turn a hub that is down
  into a commit that is silently never built, and a pass that never runs
  and says nothing is worse than one that runs twice. Also in "Two sharp
  edges".
- **The declaration is read twice** on a submitting run — once here for
  `schedule.if_moved`, once inside `submitting()` for the command.
  Deliberate: the alternative is a second way of resolving a declared
  command, and one of the two would drift.
- **`std::fs::File::try_lock`** is what the lock is built on (stable
  since 1.89; this flake is rustc 1.98.1). Probed first, on this host,
  with a two-handle and a two-thread case: `flock` conflicts between
  separate open file descriptions **in the same process**, which is what
  makes the two-thread test valid and not a tautology. No new dependency
  was added to `herdctl`.
- **One sibling task is also in `herdctl`.** Exactly what this branch
  touches there: `src/moved.rs` (new file), `src/lib.rs` (one added line,
  `pub mod moved;`, after `pub mod declaration;`), `src/checkout.rs` (71
  lines added at the **end of `impl Checkout`**, after
  `refuse_if_unpushed`; nothing existing edited), `src/declaration.rs`
  (19 lines added **between** `Commands::resolve` and
  `Commands::no_such_command`; nothing existing edited), `src/main.rs`
  (the `Action::IfMoved` variant added **after** `Action::Submit` and
  before `Action::WouldRun`; its dispatch arm added **after** the
