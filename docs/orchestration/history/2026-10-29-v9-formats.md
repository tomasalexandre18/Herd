Three public formats that were promised stable in prose are now asserted as

**What each one actually prints, verified before anything was written.**

The `ran on:` line is, byte for byte:

```
ran on: server (the only runner offering kvm; herd output format 1)
```

Its only variable parts are the runner's own name and the hub's free-text
reason, both arguments of `herd_proto::ran_on_line`; they are named in the
test and supplied by it. Everything else — the eight-byte prefix, the space
before the parenthesis, the `; herd output format N` that rides *inside* the
parentheses (D109), the closing parenthesis with nothing after it — is
frozen. The reader side is pinned too, and deliberately **not** as a round
trip: `ran_on_parts` is fed the frozen *literal*, because a round trip stays
green when the formatter and its inverse move together, which is exactly the
change that breaks every consumer who wrote their own reader against
`^ran on: (\S+) \((.*)\)$`.

`OUTPUT_FORMAT_VERSION` has exactly one printed surface in the whole of Herd
— that line — so it is frozen in both places: as the number **1**, and as the
suffix `; herd output format 1)`.

The verdict document is frozen as three whole files, read back through
`Verdict::write_to` so that the pretty printing and the final newline are
part of the freeze and not just the serializer's output:

- a job a cap stopped, with **every** field of the document carrying
  something: the cap's figures, both commits and their disagreement, a
  sentence in `said`, and `metrics` down to the per-resource pressure;
- a job that passed, which is the document a consumer's wrapper reads most
  often, with its four `null`s;
- a run that got no outcome at all (`"cause": "no_verdict"`).

Every variable part is an input and is supplied by name: the job id, the
runner and the reason, the two commits (forty hex, spelled out in the
expected text rather than computed), the cap's figures, the sentences, and
all of `metrics` — which is the one genuinely measured part, so it is given
fixed figures rather than measured. The only path touched is a `tempfile`
directory whose name never reaches an assertion. Nothing depends on a
hostname, a path, a timestamp or a duration.

**The failure messages argue against the wrong repair.** Each file carries a
`WHEN_THIS_FIRES` constant, interpolated into every assertion, which names
the two honest repairs — revert the unintended change, or move the format
version in the same commit — and says that pasting new output over the
expectation with the version left where it was is the one repair that is
always wrong, because it tells every consumer's parser it is reading a format
it is not. The verdict file's message carries the asymmetry the format
actually has: *adding* a field leaves `VERDICT_FORMAT_VERSION` alone and is
an expectation updated there on purpose, while *removing* one or changing
what one means is a bump.

**Doc comments now point at the machine behind the promise**:
`OUTPUT_FORMAT_VERSION`, `VERDICT_FORMAT_VERSION` and `ran_on_line` in
`herd-proto/src/lib.rs`, and the module header of `herdctl/src/verdict.rs`.
Doc comments only; no code changed.

**Three numbers locked, none moved.** `OUTPUT_FORMAT_VERSION` 1,

## Risks and findings

1. **A documentation inconsistency, flagged and not fixed.** `docs/plan.md`
   line 532 states Q7 as "`ran on:` line, status JSON and event payloads each
   carry a format version". The `ran on:` line does. The hub's records carry
   `record_version` (`RECORD_VERSION`, `herd-hub/src/job.rs`, read back in
   `report.rs:344` and `retention.rs:545`) — a version, under another name,
   and not one this task could check from outside. **No `format_version` of
   any kind exists anywhere in `herd-hub/src`**, so "event payloads each
   carry a format version" has nothing behind it that I could find. Q7's
   third surface therefore looks unmet, and the verdict document — frozen
   here, versioned by D166 — is *not* one of Q7's three. Fixing that is a
   product change and it touches the hub, so it stops here as a finding.
2. **E-02's line is quoted short in two docs.** `docs/coverage.md` line 19
   and `docs/plan.md` line 163 both write the line as
   `ran on: <runner> (<why>)`, with the closing parenthesis straight after
   `<why>`. What is printed is `(<why>; herd output format 1)`. This is **not
   a defect**: D109 decided the version rides inside the parentheses
   precisely so that a reader anchored on `^ran on: (\S+) \((.*)\)$` still
   matches, and `herd-proto`'s own doc comment says so. But a reader of
   `coverage.md` alone would write a reader that rejects the real line, and
   `docs/joining.md` line 306 shows the full form. Behaviour frozen as
   printed, per the brief; the short form in those two rows is worth one
   clause each, and is a prose change for whoever owns those rows.
3. **The frozen verdict text will need updating when a field is added, and
   that is correct, not a flaw.** `VERDICT_FORMAT_VERSION`'s own rule is that
   adding a field does not move it, so a future field is an expectation
   edited here *on purpose*. The failure message says so in as many words, so
   that the one legitimate edit cannot be used as cover for the illegitimate
   one.
4. **What is frozen is `ran_on_line`'s output, not the hub's `why`.** The
   reason text itself is composed in `herd-hub` (`server.rs`, which this task
   must not touch) and is free text by design — D109 makes it part of the
   `(.*)` a reader must tolerate. A consumer who parses *inside* the
   parentheses is outside the promise, and no test here gives them one.
5. **No end-to-end assertion was added.** The goldens are unit-level, on the
   two functions that compose these bytes and on the file `write_to` writes.
   The existing end-to-end tests that assert the real line on a real
   `herdctl`'s stdout (`herdctl/tests/exit_code.rs:265`,
   `declared_end_to_end.rs:62`, `outputs.rs:199`,
   `herd-hub/tests/real_herd/mod.rs:1199`) still do their job, and they build
   the expected text from `herd_proto` rather than keeping a copy, which is
   what invariant 4 asks. So the chain is: the end-to-end tests prove the
   real binaries print *what the formatter returns*, and these prove the
   formatter returns *these bytes*.

## Decisions needed

**Question.** Q7 names three versioned surfaces and only one of them —
the `ran on:` line — demonstrably carries a format version; the verdict
document, which is the second thing a requester parses, is versioned under
D166 and is not in Q7's list. Should Q7's row be restated to the surfaces
that exist (the `ran on:` line, the record's `RECORD_VERSION`, the verdict
document), with "event payloads" either dropped or made a named gap?

**Recommendation.** Restate the row, as a prose-only task, before v1.0.0:
the row is read as a promise and currently over-promises. The code is right;
the row is stale.

**Fallback.** Leave it, and let whoever meets a consumer's question about
event payloads discover it then. Cheap now, expensive at exactly the wrong
moment.
