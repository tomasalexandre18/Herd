## Done

**`herd-runner/src/packstore.rs`** (+1427 / −19). Nothing else in the crate
is touched: *Owns* was this one file and it held.

1. **`PackStore::evict_to_budget(&Claims) -> Result<Swept, String>`**, the
   runner's own gc. It takes **whole packs** and never part of one. Under it:
   - **never what a queued or running job references** (`Claims::referenced`);
   - **never the newest `keep_per_key` of a key family the keeper pins**
     (`Claims::pins`, the `PinPacks` frame itself rather than a second
     vocabulary);
   - **the newest `Claims::keep_per_key` of every key family are taken
     last** — `KEEP_PER_KEY` = 5 by default, configurable per call. **A
     preference and not a floor**, said in the type's own doc: a store ten
     gibibytes over its figure has to come under it, and the done-when
     protects what is *pinned and referenced*, not what is merely recent;
   - **no candidate destroyed that frees nothing**, because every object of
     it is named by another pack this store holds — and it says so;
   - **nothing at all without a budget**; absent is nobody said, never nought;
   - **nothing under `packs/refused/`**, which it cannot reach: it reads
     `manifests/` and `objects/` and knows no third directory.
2. **The order is ORCH-240's obligation, discharged where the divergence
   would be caused.** A victim's manifest directory is `rename`d aside under
   `EVICTING_PREFIX` (`.evicting-<pid>-<n>`, a name `check_object_digest`
   cannot read as a pack id) **before any object of it is unlinked**, then
   the objects no remaining manifest names, then the directory. From the
   rename onward the pack is **absent**, so every id `held_packs` still
   returns is still whole. Objects first would leave an instant in which this
   runner announced a holding it could not serve.
3. **A kill mid-eviction leaves the store whole-or-absent, and the next pass
   finishes it.** The moved-aside directory still holds the manifest that
   names the objects, so a later pass unlinks the ones nothing live names and
   removes the directory. That resume runs **before the budget is even read**,
   because finishing a removal already decided is not spending a budget — a
   store whose operator never set one would otherwise carry those bytes for
   ever.
4. **An object another manifest still names is kept.** One reading of
   `manifests/` per pass counts how many packs name each object; a count
   above one is decremented and the file left alone.
5. **A pack's key family is written down**: `KEY_FILE` (`pack.key`) beside
   the manifest, a JSON array of strings, **additive, idempotent and
   sorted** — one content really can be two families, and a last-writer-wins
   file would move a pack between families on a replay. `remember_key` is
   called from `leave_packs`, where the key is known. A JSON array and not a
   line per key because a `leaves` key is the requester's own word and
   nothing in Herd forbids a newline in one.
6. **`Shared::work`**, one lock per data root, held for the whole of an
   `ingest` and the whole of an eviction. **A correctness lock, not a
   performance one, and the property it buys is ORCH-240's**: an ingest skips
   an object the store already holds and writes its manifest last, so without
   it an eviction can take away the very object the ingest decided it need
   not place, and the ingest then files a manifest for a pack this runner
   announces and cannot serve. The cost is that two ingests no longer
   overlap, which is a concurrency nothing in this runner uses today — one
   collection per attempt, one fetch per needed key. `PackStore` now carries
   `Arc<Shared>` (the figures plus that lock) in place of
   `Arc<Mutex<Standing>>`; `standing_for` became `shared_for` and the key is
   still `keyed()`'s, so P1's path-identity fix is untouched and
   `two_spellings_of_one_data_root_are_one_store` is still green.
7. **The figure it spends is measured at both ends.** `measure()` at the
   start and at the end of a pass, not the running total: every other reader
   here does arithmetic because an announcement must not walk, and this is
   the one act already walking `manifests/` — and the one act where being a
   rounding out would destroy a pack for nothing. The running figure is moved
   by each unlink, so a reader of `usage()` between two victims is never told
   the store holds bytes that are gone. P1's own counter test,
   `saying_what_this_runner_holds_lists_no_objects_directory`, is still
   green: **the announcement still lists `objects/` zero times.**
8. **`Swept`** carries `budget`, `bytes_before`, `bytes_after`,
   `bytes_freed` (what was really unlinked, never what was named),
   `packs_removed`, `objects_removed`, `within_budget` and `said`. A pass
   that could not reach the budget is `within_budget: false` with a sentence
   naming all three reasons; it destroys nothing to pretend otherwise.
9. **Module doc restated.** *"Nothing here evicts anything"* is gone, rule 3
   now names the gc among the four things that never touch the set-aside
   area, and the doc says in as many words that **nothing calls the gc yet**.

## Risks and findings

1. **A kill after the rename and before the last unlink can strand objects
   permanently if that store is never swept again.** The resume reads
   `.evicting-*` directories, so a later pass finishes the job; but if the
   kill lands *after* the directory is removed and before the last object
   goes — which cannot happen, the directory is removed last — or if the
   manifest inside it will not parse, the objects it named are orphans. They
   **still weigh in `usage()`**, so the budget goes on bounding the disk, and
   the next ingest of that pack places none of them a second time; what is
   lost is the space until then. **No orphan sweep was written on purpose**:
   a sweep of objects no live manifest names would, run beside an ingest,
   take the objects that ingest had just placed and not yet filed a manifest
   for — the very ORCH-240 hazard, in a worse form, since it would hit a pack
   nobody had chosen. `Shared::work` closes it for an eviction and would have
   to be held by the sweep too; the honest answer is that a sweep is its own
   task with its own test and not a rider on this one. Drafted as a row.
2. **`remember_key` runs just outside `Shared::work`.** `leave_packs` calls
   `ingest` (which takes the lock) and then `remember_key` (which does not),
   so an eviction between the two would make the key write land on a
   directory that is gone: `write_fsynced` then refuses by name, `said`
   carries it, and the pack is held as one of no key family. It cannot be
   folded inside the lock because `std::sync::Mutex` is not reentrant and
   `ingest` does not know the key. Nothing calls the eviction today, so the
   window is unreachable in the field; it is named rather than left to be
   found.
3. **A single unreadable manifest refuses the whole pass.** `read_manifests`
   propagates `manifest_of`'s refusal, which is the safe arm and not the
   strict one: a pack left out of the reading is a pack whose objects nothing
   accounts for, so the next candidate sharing one would have it unlinked
   from under a pack this runner announces. The consequence is that one
   hand-edited directory blocks eviction until an operator removes it — and
   `manifest_of`'s own refusal already says to do exactly that. `held_packs`
   announces that pack meanwhile, which is pre-existing and ORCH-240's own
   named consequence.
4. **`packs/incoming/` is outside the budget**, finding 3 of *Not done*.
   Measured by reading: `objects_bytes` lists `packs/objects/` and nothing
   else, and `fetch.rs` stages under `packs/incoming/<nonce>/objects/`.
5. **The 10 GiB figure is real and the disk cost is 512 bytes per object.**
   The fixtures plant **sparse** objects (`File::set_len`), because what an
   eviction reads of an object is its name and its length — it hashes
   nothing, `ingest` already did — so the arithmetic under test is the
   shipped arithmetic on the shipped figures. A test that really wrote ten
   gibibytes would not be run twice on a host shared with the first
   consumer's production. Stated here because it is the one place a reader
   could think the figure was faked rather than deferred to the filesystem.
6. **Two of my own test fixtures passed for the wrong reason and were
   rebuilt.** The first version of the keeper-pin clause used the same figure
   for `pins.keep_per_key` and `Claims::keep_per_key`, so the pinned packs

   code deleted; the first version of the retention clause used one family of
   eight, where per-family order and age order coincide, so it stayed green
   with the tier deleted. **Both were found by running the red
   demonstration, not by reading** — which is the whole argument for the

### The `docs/decisions.md` entry

```markdown
## 2026-10-30 — D-NEXT Newest-five per key family is a preference, not a floor

M12's plan asks the runner's eviction for "newest-N-per-key-family kept
(N = 5, configurable)" beside "never what a queued or running job
references, never what the keeper role pins". Read as three floors, the
sentence cannot be met: a store ten gibibytes over its budget whose every
key family holds five packs has nothing it may take, and the budget an
operator set stops bounding their disk.

**So there are two kinds of keeping, and only two of the three are
absolute.** What a job references and the newest `keep_per_key` of a key
family the hub pins are **never** evicted, whatever the figure says —
those are the two the milestone's own `Done when` names, and taking
either is the runner destabilising its own work or breaking the fleet's
custody. The newest `KEEP_PER_KEY` of each key family are evicted
**last**, after everything else, and they are evicted if the budget
cannot be reached otherwise. A pass that still cannot reach it says so,
with all three reasons named, and destroys nothing to pretend otherwise.

`KEEP_PER_KEY` is **5** because `docs/plan.md` M12 says 5 and no
derivation of that number exists anywhere — measured by the planning
pass of 2026-10-30. It is therefore a default and never an acceptance
criterion: `Claims::keep_per_key` carries whatever the caller wants.

Two consequences, both deliberate. A **key family** has to be on the
disk, because a pack is its manifest's bytes and cannot carry a
requester's key: it is `packs/manifests/<id>/pack.key`, a JSON array,
additive, since one content really can be two families. And a candidate
whose every object another pack still names **frees nothing** and is
kept: destroying a pack to recover no bytes is the one move a byte
budget can never justify, which is the same rule `disk-policy.md` states
for the hub's own sweeper one store over.

**The hub does not enforce any of this.** The budget is the machine
owner's figure and the gc is the runner's — `herd-proto`'s own words,
quoted in M12's plan: "a hub that compared usage against a figure of its
own would be enforcing a bound the machine's owner never agreed to".
```
