The test stays `#[ignore]`d with its reason unchanged — `a bench; run it

**ORCH-158's open question is answered: `recover` is cleared.** The row
said *"whether the pending queue order depends on read order is for
whoever takes this row to establish, not to inherit"*. It does not, and
not by inspection of one line: `recover` sorts the sequences it derives
from these names (`sequences.sort_unstable()`) **before it reads a
single record**, its pending queue is a `BTreeSet`, its deduplication
links take `min(sequence)` per key, and its quarantine list is a
`BTreeMap`. So startup already read in id order and R0 changes nothing
there. The saving lands on `collections_owed` (the 3.29 s cold walk at
33 340), on the retention pass **R6** will write, and on `registry.rs`.

`registry.rs` is the one place where sorting changes an outcome rather
than a cost, and it changes it for the better: when two published packs
claim one `(commit, key)`, `rebuild` keeps the **first** read in
`by_key`, which was the hash order's arbitrary choice and is now the
lower pack id. The conflict is recorded in `conflicts` and refused
either way, so nothing resolvable changed — it became deterministic.
Both facts are in the function's own doc.

### R9 — ORCH-097: `retention-preview` answers the budget's question too

`herd-hub/src/retention.rs` and `herd-hub/tests/retention_preview.rs`,
plus one paragraph in `docs/operating.md` so that the shipped
subcommand's own documentation is not left describing half its output.
**`herd-hub/src/main.rs` is untouched**, which is the mechanical proof
of *no new CLI surface*: there is still no `--apply` and no flag at all
that a later change could invert, because no argument was added.

One tool, one walk, two questions:

- `RetentionPreview::sweep` is a `SweepPreview`: what `files/` holds
  over every job directory a sweep counts (**the figure a budget is
  compared against**), the candidates in the sweep's own order, and the
  bytes a sweep counts and **cannot** free, one `Withheld` each with its
  reason.
- **One walk.** The job directory is weighed once, at the top of the
  loop, and that one `read_dir` answers the span's three populations and
  the budget's one. `Weighed` now splits the collected bytes it already
  measured into `files/`, `files.part/` and `files.gone/` instead of
  measuring them again.
- **No budget argument, and that is the design decision.** The hub's
  `--output-budget` is the serving hub's own argument and no byte of a
  state root records it, so rather than answer for one figure the
  preview prints the sweep's order with `freed_by_then`, a running total
  of what is freed by the time each candidate is gone. An operator reads
  down that column until it reaches `held − budget`: any budget,
  including the one they are thinking of moving to, at no further cost.
  The test does that arithmetic as an assertion rather than leaving it
  to the prose.
- **The floor is the one key it cannot order on, and it says so.** The
  sweep's first key is `--output-floor` — outside the floor before
  inside it — which this tool is not given either. The printed order is
  the sweep's on keys 2, 3 and 4 (passed before failed, fetched before
  never fetched, oldest first), which is the sweep's order *within one
  floor band*; under a floor of `F` every candidate younger than `F`
  moves to the end and keeps that order among themselves, because the
  partition is stable. Each candidate's age is printed for exactly that
  arithmetic.
- **Faithful to `store.rs`'s sweep and not a second definition.** The
  four refusals are its four `continue`s in its order — no readable
  record (a missing `job.json`, another layout's version, labels this
  hub rejects, outputs this build cannot parse), not over, already
  removed, and a collection that is not whole — and each adds the bytes
  to `could_not_free` there and to `withheld` here. `files.part/` is
  never a candidate, a `files.gone/` is counted as what a sweep gives
  back before it chooses anything, and a directory in `jobs/` whose name
  is not a job id is neither held nor freeable and gets its own line.
- **ORCH-124's known leak is visible for the first time.** "1 kB held"
  is not actionable when 900 bytes of it are unfreeable, and until now
  nothing printed which bytes those were or why.
- **The two questions differ, and the fixture shows it in one line.**
  `j0000000008` is a `producer` whose span is `0`: it NEVER EXPIRES in
  the per-class block above, and it is the **first** collection a sweep
  would take, because the output budget does not look at a record's
  class at all. An operator reading only the span side would have
  concluded those bytes were safe.
- Printed under a refusal too, unlike the per-class figures: the two
  `Verdict` refusals are about the clock and the spans, the sweep's
  order is three record fields and a file length, and the one
  clock-derived figure in the block is named where the refusal is.

Four new tests (11 → 15 in `retention_preview.rs`, all green), and the
whole rendered text of the fixture is still asserted byte for byte with
the new block in it. Every new test re-asserts `listing(root)` — path,
length **and** mtime of every file under the root — so *"it removes
nothing"* stays an assertion.

## Risks and findings

1. **The plan's 0.41x at 33 340 did not reproduce; 0.50x did.** Both
   runs are inside the stated band, and the direction of the difference
   is the one that matters to R6: the saving is flat in `T`, so a cold
   startup pass at ten times the consumer's directory count halves and
   does not better that. This run was taken at load 1.7-2.0 on 12 cores
   and the figure is a within-run ratio, so load affects both halves
   alike — but it is one run, and the earlier one was a different build
   and a different hour. **Finding, not a correction.**
2. **R0 does not shorten startup today, and the plan's sentence implies
   it does.** *"it halves exactly the startup pass R6 has to bound"* is
   true of the pass R6 will write and false of the pass that exists:
   `recover` already sorts. Nothing in the plan breaks, but R6's brief
   should not inherit the belief that startup got faster at this
   landing.
3. **The preview now weighs every job directory, not only the judgeable
   ones.** That is required — the sweep counts the bytes of a directory
   whose record will not read, and that population is the leak — but on
   a root with many unreadable records it is more `read_dir` calls than
   before. The tool is run by hand, takes no lock and reads read-only,
   so this is cost and not risk; it is written down because it is a
   change in what the walk does and not only in what it prints.
4. **The sweep side parses each `job.json` a second time** (as
   `Sweepable`) rather than widening `Judgeable`. Deliberate: folding
   `outputs` into `Judgeable` would make a record whose `outputs` this
   build cannot parse vanish from the **span** figures too, which is a
   figure nobody asked to change. One read of the disk, two parses of
   one string.
5. **`ID_DIGITS` is now duplicated** in `retention.rs`, as `LOG_FILE`
   and `LOG_SEQ_FILE` already were and for the same reason: it is
   private to `store.rs`, which is another task's. Held by a figure and
   not by a comment —
   `a_directory_in_jobs_that_is_not_a_job_holds_bytes_a_sweep_ignores`
   mints a real job through the store and asserts that its id lands
   among the candidates while a directory beside it does not.
6. **`collection_is_whole` is replicated too**, by necessity, and it is
   the one replica that could drift silently: if `store.rs` changes what
   *whole* means, the preview would promise bytes a sweep would not
   free. The test that would catch a rename is the store-backed one; a
   change in the **rule** would not be caught, and R3 is the task that
   touches that rule.
7. **No `files.gone/` was removed, and a real sweep removes them.**
   `sweep_now` deletes a leftover tree before it chooses anything; the
   preview counts it and leaves it, which is the only honest reading of
   *"it removes nothing"*. So `leftover` is a figure a sweep would
   recover without destroying any evidence, and it is labelled that way.
8. **Another step was running beside this one** on
   `herd-runner/src/packstore.rs` and `main.rs`. No file of this branch
   overlaps it; `cargo clippy --workspace --all-targets` compiled every
   test crate in the workspace, which is what would have caught a
   protocol struct widened under us.

### `docs/decisions.md` — first entry

```markdown
## 2026-10-30 — D-NEXT Every directory listing in the hub is in id order

ORCH-104 measured that reading the hub's records in ext4's
directory-hash order costs **twice** what reading the same records in
id order costs on a cold page cache — 0.47x at 3 334 directories and
0.50x at 33 340 on this host, re-measured at this landing, with the
pair run in both sequences and a warm control showing no difference at
all — and that **zero of 33 341** names come back in the same
position. **Decided:** `durable::names_in` sorts, so there is one place
where the hub's listings are ordered and every caller inherits it. A
job id is `j` and a fixed width of zero-padded digits, so byte order is
id order is creation order, which is how the files were laid down.

**No caller's behaviour changes, and that is established rather than
assumed.** `recover` sorts the sequences it derives from these names
before it reads a record, keeps its pending queue in a `BTreeSet`, its
deduplication links at the lowest sequence per key and its quarantine
list in a `BTreeMap` — so startup already read in id order and this
buys it nothing. `collections_owed` returns a `Vec` its caller consumes
with no lock held, recomputed at every redial (D79): advisory, and the
walk the 2x applies to in full. `sweep_now` overwrites a total it is
allowed to let drift (D152) and sorts its candidates on four keys
afterwards, so read order survives only as the tie-break between two
records equal on all four including `ended_at` to the nanosecond.
`registry.rs`'s `clear_staging` removes every name it is given.

**The one outcome that changes, changes from arbitrary to
deterministic:** when two published packs claim one `(commit, key)`,
`registry::rebuild` keeps the first one read, which was the hash
order's choice and is now the lower pack id. The conflict is recorded
and resolution refuses it either way.

**What this does not buy.** The saving is flat in the directory count,
not growing: 0.47x at 3 334 and 0.50x at 33 340 in this measurement
against ORCH-104's 0.50x and 0.41x. So it is a halving of a cold walk
at both populations, and M12's record-retention pass should be sized
against that and not against more. Warm, there is nothing in it: the
first walk after a start is the whole of the gain.
```
