## What changed and why

**M12 Track P step P5.** The hub can now name the runners that keep a
pack, fills `Welcome.keeper_for` from that policy, and sends
`FromHub::PinPacks` when the set a connected runner keeps moves.
`herd-proto` is untouched: every frame was already on the wire at
`PROTOCOL_VERSION` 3, which is the planner's M12 hypothesis H-A holding.
This is the half of custody the hub owes; the runner's half landed in
batch 23.

**What `main` can do now that it could not before.** An operator may
pass `herd-hub --keeper RUNNER` to name a default keeper and
`--keeper-for KEY=RUNNER` (repeatable, comma-separated in
`HERD_KEEPER_FOR`) to move one key family off that default onto a named
runner. A keeper is then told its families at its welcome and told again
by `PinPacks` whenever its own set really moves — an empty frame being
how custody is retracted — and a runner whose set did not move is sent
nothing at all.

**And what it does NOT make true, because the name invites the other
reading.** Neither setting has a default. A hub given neither names no
keeper, carries `keeper_for` on **no** welcome and sends **no**
`PinPacks` — byte for byte the behaviour of `83bc78a`. **The consumer's
hub passes neither, so nothing is pinned in production and nothing has
changed there.** A pack outliving the machine that built it is M12 P7
and still needs M11's push path, so nothing in this landing says custody
works end to end. The branch's author asked that no report claim it, and
was right to.

**Which expectations come with it.** E-16 moves, not closes:
`cut-v1.0.0`'s scope table counts E-16 as partly built and **needs
re-reading after this landing**, which is in *Left out*. E-14 and E-23
are untouched by this step.
