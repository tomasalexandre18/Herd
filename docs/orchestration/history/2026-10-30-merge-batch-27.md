## Risks and findings

1. **The conflict was in the file nobody watched.** Every party named
   `server.rs` and it merged clean; `pack_frames.rs` was named by nobody
   and did not. The reason is worth keeping: a shared *arm* is a
   semantic overlap people can reason about, and a shared **append
   anchor at end of file** is not — it is a property of where a test
   file grows, which is the same place for every author. Two branches
   adding tests to one file will collide there whatever their subject.
2. **A drafted board cell can be malformed in a way only the merger
   sees.** Two of the ten rows carried a two-clause State cell, which
   `check-docs.sh` rejects; both read naturally in a handoff and neither
   author could have run the board check, because neither touched the
   board. The merger normalising them is the right place, and it is
   recorded above rather than done silently.
3. **A drafted decision header can be over-long for the same reason.**
   D272's was 86 columns because it was written inside a fence, where the
   79-column rule does not measure it. One of the four authors wrapped
   his header by hand and the others did not; the rule is the file's, not
   the fence's.
4. **`status.md` at its cap is a standing cost, not this batch's.** It
   fit this time only because a whole section was folded into the
   preamble. The next landing that adds two facts will face the same
   choice, and the honest answer then is the same as it was here:
   replace, and name what went.
