## What changed and why

**A live data-loss defect becomes legible on the record, and a test's
detector is proven.** Batch 35 made the hub *ask* for a collection at
the verdict (**D291**); this batch makes the hub *write down* the times
it gives up on one (**D292**). The first consumer's 2026-10-31 loss —
17 files, 42 MiB under a record reading `finished, exited 0` — was
derivable from the manifest and `files/` all along, and **nothing
derived it**: both durable witnesses were the hub's own stdout, which is
not a record, and the third was a client log. A nightly reading that
record saw a green job.

So `main` can now do one thing it could not before: a reader of a job's
`events.jsonl` is told, in one greppable line, that a collection was
given up on and by how much it fell short — files here of files owed,
bytes here of bytes owed, the runner, and the same sentence the
requester was given. Hub only. **No frame changed, no
`PROTOCOL_VERSION` move, and `RECORD_VERSION` stays 2.**

Alongside it, ORCH-321's last owed evidence lands: the hollow-green
control for `a_link_cut_while_the_runner_is_full_loses_no_job`, which
proves that detector fires on the pre-D182 defect it is named for. No
product source is committed by that branch.

**`RECORD_VERSION` stays 2, and the warrant is honest about its own
limit.** The letter of that constant's doc does **not** cover this: it
speaks of `#[serde(default)]` **fields**, not variants, and this is the
first event kind added since the number reached 2. The ruling is stated
in D292 rather than assumed — **an event kind is additive because a
line's absence has always meant the thing did not happen** — and it is
left stated, not smoothed over.

**What an older reader sees, in three distinct cases**, which must
survive this landing because the first consumer parses `events.jsonl`
themselves:

1. a rolled-back v1.0.0 **hub binary** is unaffected: nothing in the
   product reads the file back;
2. a reader that decodes into v1.0.0's `JobEvent` gets **a hard error
   for the whole job's history**, not a skipped line, because
   `JobEventKind` is `#[serde(tag = "event")]` with **no
   `#[serde(other)]` arm**, and `JobStore::job_events` fails the whole
   call for that job;
3. their own parser's behaviour is theirs, not ours.

**A benign race, named and not hidden.** The one-shot's "already
written?" test holds no lock, because `job_events` takes the lock itself
and this store's is not reentrant, so two interleaving callers could
write the line **twice** — a duplicate on a history, never a wrong
figure. What the test is for is the unbounded case, a line per late
`herdctl wait --outputs-to` for ever. Making it exact needs a record
field, which is a second format change in one branch, and it was
refused on that ground.

**Two in-tree comments were amended, and a design statement being
re-grounded deserves more than a diff.** Both read, as written, as a
**rule freezing the variant list** — *"a new variant would make the file
undecodable to a hub rolled back"*:

- `herd-hub/src/store.rs`, `readmit_to_the_budget`'s *"No
  `events.jsonl` line"* paragraph;
- `herd-hub/src/store/ordering_oracle.rs`, the oracle's step 17 comment
  on that same path.

Neither fact changed — the arm is still absent — but each is
re-grounded on the reason that actually holds, which is that the
`outputs_removed` line already on the history stays true and there is
